# Читабельность артефактов: системный отчёт

> Ветка: `feature/artifact-readability` · только анализ, без правок кода.

## 1. Goal и JTBD

**Goal:** артефакты PoV-генератора должны читаться как тексты, прошедшие редактора — без слов-наполнителей, со смыслами на местах, в режиме «10 минут → принял решение».

**JTBD:**

- **Заказчик документа** (CTO / бизнес-владелец): прочитать ТЗ за 10–15 минут и решить «запускаем / не запускаем», не тратя время на перевод консультантского жаргона.
- **Автор системы** (мы): доверять выводам собственного сервиса; не стыдно показать артефакт «как есть», без ручной правки.
- **Команда исполнения** (продукт + разработка): найти конкретику (требование, метрику, ответственного) без необходимости вычитывать абзацы воды.

Все три заказчика проигрывают от одной и той же поломки: **система оптимизирует полноту, а не плотность**.

## 2. Root cause: почему артефакты раздуваются

Шесть системных факторов в текущей реализации, отсортированы по «силе вклада в верcosity»:

### 2.1. `<output_contract>` сам требует объём
`execution_service.py:697–704`:

> «в array<string>-полях каждый item — развёрнутая формулировка из 1–3 предложений ... а не телеграфный bullet».

Это **прямая команда модели писать длиннее, чем нужно**. Принцип «минимально необходимое» в системе нигде явно не закреплён — есть только запреты конкретных штампов в `<style_bans>`.

### 2.2. Schema-forced completeness
`artifact_contracts.py`: для `requirements_spec` обязательны 12+ полей, для `normalized_request` — 6 секций, для `business_outcome_model` — 8. Все required. Если контекста на раздел не хватает, у модели только два пути: оставить пусто (получит blocking finding от `_validate_enterprise_spec`) или налить воды. Она выбирает второе.

### 2.3. Markdown-рендерер визуально приглашает к заполнению
`artifact_contracts.py:1634+`: 30+ функций рендеринга, каждая печатает заголовок секции даже при пустом списке. Раздел `## Неявные риски` с одной строчкой «нет существенных рисков» выглядит сиротливо — модель «помогает» дополнить.

### 2.4. Асимметричная валидация
`validation_service.py:_validate_enterprise_spec` (419–443) проверяет **только непустоту**. Нет ни одной проверки на:
- среднюю длину предложения;
- долю стоп-слов / канцеляризмов;
- повторение мыслей между секциями;
- избыточные модификаторы.

Feedback loop работает только в одну сторону: «мало → переделай»; «много, но плохо» система не видит.

### 2.5. Один system_prompt на все 30+ artifact_role
`_build_prompt` собирает одинаковую «шапку» для всех типов: и для `executive_summary` (где нужно 5 пунктов на полстраницы), и для `requirements_spec` (где нужна полнота), и для `alternatives_analysis` (где нужна таблица сравнения). Стиль не дифференцируется по жанру артефакта.

### 2.6. Принципы «Пиши, сокращай» представлены частично
В `<writing_principles>` и `<style_bans>` уже есть: Минто, MECE, активный залог, конкретика, бан вводных мета-фраз, канцелярита, промо-лексики, кальок. **Нет**:
- стоп-усилителей (очень, крайне, заметно, существенно, значительно);
- теста «вычеркни — пострадал ли смысл»;
- правила «один абзац — одна мысль»;
- информативных заголовков («Что входит в этап» вместо «Скоуп этапа»);
- параллелизма в списках (грамматически однородные элементы);
- запрета смешения тонов в одном артефакте;
- запрета модальных смягчителей без позиции («возможно стоит рассмотреть») — есть только в одной формулировке, не вынесено в pre-flight.

## 3. Опции воздействия

Пять рычагов, можно комбинировать. Колонки: эффект / стоимость внедрения / риск регрессии.

| # | Рычаг | Эффект | Стоимость | Риск |
|---|-------|--------|-----------|------|
| A | Перепрошивка system_prompt | средний-высокий | 1 файл, ~1 день | низкий |
| B | Опциональность полей + умный рендерер | высокий | 2 файла, ~2 дня | средний (миграция артефактов) |
| C | Editor pass — отдельная LLM-стадия «ужми на 25–30%» | очень высокий | +1 LLM call/артефакт, ~3 дня | средний (стоимость, время) |
| D | Style metrics в валидации | средний (даёт измеримость, без неё A/B/C слепы) | 1 файл, ~1 день | низкий |
| E | Дифференцированные промпты по жанру артефакта | средний-высокий | refactor _build_prompt + 30 шаблонов, ~5 дней | высокий (дрейф между жанрами) |

### A. Tuning system_prompt
Минимально-инвазивно, можно сделать за один коммит:

1. **Снять или переформулировать «1–3 предложения»** в `<output_contract>`. Заменить на: *«пиши минимально необходимое количество слов, чтобы смысл был полным и однозначным; если для item достаточно одной формулировки — одна формулировка»*.
2. **Добавить в `<writing_principles>` блок «Плотность»**:
   - тест «вычеркни слово/фразу — смысл пострадал?». Если нет — это была вода;
   - один абзац — одна мысль; вторая мысль = второй абзац;
   - заголовок информирует, не интригует;
   - элементы списка грамматически параллельны;
   - не смешивать тона в одном артефакте.
3. **Расширить `<style_bans>` стоп-усилителями**: «очень», «крайне», «заметно», «существенно», «значительно», «достаточно» (в роли усилителя), «в целом», «по сути», «как правило», «безусловно».
4. **Расширить `<style_bans>` модальными смягчителями без позиции**: «возможно», «вероятно», «при необходимости», «по усмотрению», «в случае необходимости» — если у автора есть позиция, она должна быть высказана; если нет — поле `open_questions`/`assumptions`.
5. **Добавить в `<pre_flight_check>` пункт 6 «COMPRESSION TEST»**: пройтись по тексту и удалить всё, что можно удалить без потери смысла.

Эффект — ожидаемо 15–25% сокращения объёма, без потери информации. Подтверждается только метриками (см. D).

### B. Опциональность полей + умный рендерер
Корневая правка модели данных:

1. В `artifact_contracts.py` перевести «слабые» поля из required в optional с инструкцией в `description` поля: *«опусти, если для раздела нет содержания из контекста; не заполняй ради заполнения»*. Кандидаты: `implicit_risks`, `ambiguous_points`, `value_hypotheses`, `escalation_candidates`, `future_phase_candidates`, `excluded_deliverables`, `dependency_constraints` — те, что часто пусты по природе запроса.
2. В `render_markdown` ввести правило: если значение поля — пустой массив или null, заголовок секции **не печатается**. Это меняет визуальный сигнал для модели: «отсутствие — нормальное состояние».
3. `validation_service._validate_enterprise_spec` обновить: optional-поля исключить из проверки на непустоту; required-поля оставить как есть.

Эффект — артефакты перестают иметь «секции-призраки» с одной строкой воды.

### C. Editor pass
После того как первичный артефакт сгенерирован и прошёл валидацию, отдельная LLM-стадия с промптом:

> «Ты — редактор. Сократи текст на 25–35% без потери информационных пунктов. Сохрани все факты, числа, имена, требования. Удали: стоп-усилители, тавтологии, мета-комментарии о тексте, повторы смыслов между секциями. Если в исходнике пункт списка пустой по содержанию — удали пункт. Верни JSON по той же схеме».

Стоимость: +1 LLM-вызов на артефакт. Можно делать опционально по флагу `editor_pass=true` в настройках сложности, или включать только для финальных артефактов (`requirements_spec`, `business_case`, `executive_summary`).

Эффект — гарантированный, измеримый (compression ratio как метрика), но дорогой по времени и токенам.

### D. Style metrics в валидации
Превратить «лаконичность» из субъективной категории в число. Метрики на текст артефакта (после рендера в markdown):

| Метрика | Целевой коридор | Как считать |
|---------|-----------------|-------------|
| Средняя длина предложения | 12–18 слов | разбить по `.!?`, посчитать слова |
| Доля стоп-усилителей | < 0.5% от слов | словарь из ~30 токенов |
| Доля канцеляризмов | < 1% от слов | словарь из ~50 паттернов (уже есть в `<style_bans>`) |
| Долгие абзацы (> 5 предложений) | 0 | разбить по `\n\n`, посчитать |
| Повторы лемм между секциями (Jaccard top-10) | < 0.3 | требует стемминга/лемматизации |
| Compression headroom | < 15% | сравнение с editor-pass версией, опционально |

Реализация: новая функция `_readability_findings(text)` в `validation_service.py`, которая возвращает **советующие** (не блокирующие) finding с категорией `style_density`. Они отображаются в UI и стимулируют ручную доводку или retry.

Без D опции A/B/C слепы — улучшения нечем подтвердить.

### E. Дифференциация промптов по artifact_role
Долгосрочно: разные жанры требуют разного стиля.

- `executive_summary`, `business_case`, `decision_brief` — жёсткая лаконичность, лимит на страницу, табличные блоки;
- `requirements_spec`, `non_functional_requirements` — структурная полнота важнее лаконичности; стиль формальный;
- `alternatives_analysis`, `risk_register` — табличный формат, не проза;
- `clarification_notes`, `goal_hypothesis` — диалоговый, краткий.

Реализация: вынести `<writing_principles>` и `<output_contract>` в словарь по `artifact_role`, базовый + override. Дорого, рискованно (легко породить дрейф стиля между секциями одного проекта), делать **после** A/B/D, когда базовый стиль стабилизирован.

## 4. Принципы Ильяхова, которые имеет смысл явно внести

Из «Пиши, сокращай» (Ильяхов, Сарычева) — то, чего сейчас в системе нет или есть слабо:

1. **Стоп-слова и усилители** (раздел 2.6 — см. список).
2. **Право читателя**: писать то, что нужно ему, а не то, что хочется автору. В контексте PoV — каждый раздел должен отвечать на конкретный вопрос лица, принимающего решение.
3. **Один абзац — одна мысль.** Вторая мысль = второй абзац.
4. **Тест «вычеркни и проверь».** Самопроверка в pre-flight.
5. **Информативные заголовки.** «Что входит в этап» > «Скоуп этапа»; «Метрики, по которым оценим успех» > «KPI».
6. **Параллелизм в списках.** Все элементы — одного грамматического типа (все глаголы / все существительные / все клаузы). Смешение читается как «небрежно».
7. **Один тон в документе.** Не смешивать «коллеги, давайте обсудим» и «реализация осуществляется посредством».
8. **Сильный глагол > отглагольное существительное.** «Команда поставляет» > «осуществление поставки командой». (Частично есть, усилить.)
9. **Синонимы по длине и регистру.** «Так как» вместо «по причине того, что»; «чтобы» вместо «в целях обеспечения возможности».
10. **Конкретное > абстрактное.** Уже есть в `<writing_principles>` пункт 3 — оставить.

## 5. Дорожная карта

Рекомендуемая последовательность из расчёта «максимум эффекта за минимум кода / времени»:

| Итерация | Состав | Срок | Ожидаемый эффект |
|----------|--------|------|------------------|
| **1** | A (prompt tuning) + D (style metrics, advisory) | 1–2 дня | snip 15–25% объёма, видимая метрика для дальнейших итераций |
| **2** | B (optional поля + умный рендерер) | 2–3 дня | удаление «секций-призраков», структурная честность |
| **3** | замер: на 5–10 готовых артефактах сравнить «до» и «после» по метрикам D; решение продолжать или достаточно | 1 день | go/no-go для следующих этапов |
| **4** | C (editor pass) — если итерации 1–3 не покрывают разрыв | 3 дня | гарантированный compression, но +cost/+latency |
| **5** | E (дифференциация по artifact_role) — последним | 5+ дней | финишная шлифовка |

## 6. Контроль качества: метрики и baseline

**До любых правок**: снять baseline на 5–10 артефактах, сгенерированных текущей системой. Замерить метрики из раздела 3.D. Зафиксировать в `docs/readability_baseline.md` или таблице.

**После каждой итерации**: replay тех же бизнес-запросов, перегенерация артефактов, сравнение метрик. Принцип регрессии: ни одна метрика не должна ухудшиться.

**Качественная проверка**: вручную прочитать 2–3 артефакта до/после, оценить «читаемость» по 5-балльной шкале — рейтинг должен расти от итерации к итерации.

## 7. Чего НЕ делать

- **Не вводить hard cap на длину** (типа «не больше 800 слов»). Артефакты разной природы требуют разного объёма; жёсткий лимит породит обрезку смысла или творческие способы его обхода.
- **Не удалять `<style_bans>`** под предлогом «модель и так знает». Эффективность бан-листа в промпте подтверждена эмпирически — каждый штамп, который попадал в артефакт, должен быть туда добавлен.
- **Не пытаться один раз «зарядить» промпт и забыть.** Без метрик (опция D) невозможно отследить деградацию.
- **Не делать сначала E (дифференциация по жанру).** Это финишная шлифовка, она имеет смысл только когда базовый стиль уже хорош.

## 8. Резюме

Главная техническая причина многословности — **система оптимизирует полноту в ущерб плотности**: схема обязательных полей, шаблонный рендерер и валидация на непустоту работают в одном направлении, а единственный противовес — словесные запреты в промпте, которые не измеряются.

Минимально достаточный первый шаг (итерация 1):

1. Переформулировать `<output_contract>` с «1–3 предложения» на «минимально необходимое».
2. Добавить в `<writing_principles>` блок «Плотность» (тест на вычёркивание, один абзац — одна мысль, информативные заголовки, параллелизм списков).
3. Расширить `<style_bans>` стоп-усилителями и модальными смягчителями.
4. Добавить пункт 6 `COMPRESSION TEST` в `<pre_flight_check>`.
5. В `validation_service.py` ввести `_readability_findings(text)` — советующие finding со стилевыми метриками.

Это даёт измеримую базу для всех последующих оптимизаций. Дальше — по результатам замера.
