# Harness-рантайм: Docker, песочница, установка, наглядность

Статус: проект (design). Компаньон к `2026-06-07-harness-executor.md` — тот
описывает контракт и интеграцию (шов артефакта), этот — **как агенты реально
исполняются**: жизненный цикл контейнеров, защита от перегрузки, первоначальная
установка/онбординг и наблюдаемость. Заказчик: «runtime здесь очень важен».

Зафиксировано: **выбор ноды-агента — только шаблон** (`executor: harness`),
без per-node override.

## 1. Модель исполнения: варианты и выбор

Главный вопрос рантайма — **где и сколько живёт контейнер**. Четыре варианта:

| Модель | Суть | Плюсы | Минусы |
|---|---|---|---|
| **A. Контейнер-на-прогон (ephemeral)** | На каждый лист-узел свежий контейнер: поднять → исполнить → собрать → снести | Полная изоляция, воспроизводимость, нет утечки состояния, простая очистка | Старт-латентность (~1–3 с на тёплом образе); fan-out из N узлов = N стартов |
| **B. Контейнер-на-проект (warm reuse)** | Один контейнер на прогон/проект, узлы переиспользуют рабочий каталог/репозиторий | Быстро; естественно для fan-out (общий репозиторий компонентов); инкрементальная сборка | Слабее изоляция между узлами; сложнее teardown; состояние «накапливается» |
| **C. Пул тёплых воркеров** | Небольшой пул заранее прогретых контейнеров берёт задания | Лучшая латентность под нагрузкой | Сложный жизненный цикл, ресурсы заняты простаивая |
| **D. Удалённый/hosted harness (API)** | Агент — внешний сервис, мы дёргаем API | Нет Docker у нас | Другой рантайм целиком, побочные эффекты вне нашего контроля, секреты наружу |

### 1.1 Где разница (переформулировка — решено)

Запутанность была из-за смешения двух НЕЗАВИСИМЫХ осей. Разделяем:

- **Ось 1 — жизнь контейнера.** Всегда **ephemeral**: контейнер поднимается на
  узел и сносится после. Это не обсуждается — иначе теряются изоляция, очистка и
  гарантированный kill зависшего агента. (Долгоживущий контейнер = утечки
  состояния, грязь, дыры безопасности.)
- **Ось 2 — область рабочего каталога (workspace).** ВОТ настоящая развилка:
  с чего начинает агент в узле N —
  - **per-node (свежий):** пустой каталог + только засеянные входные артефакты
    узла. Узел N НЕ видит, что «нагенерил» узел M напрямую (видит лишь
    артефакты M, если они объявлены его входом).
  - **per-group (общий том):** именованный том монтируется во все узлы одной
    «сборочной группы»; узел N видит файлы, оставленные предыдущими узлами
    группы (один репозиторий растёт инкрементально, кеш зависимостей общий).

То есть «ephemeral vs warm» — ложная дихотомия: контейнер ВСЕГДА ephemeral, а
вопрос лишь в **области workspace** (узел или группа).

### 1.2 Сценарии (когда что)

| Сценарий | Область workspace | Параллелизм |
|---|---|---|
| Один самодостаточный артефакт из спеки (отдельный скрипт/документ/обособленный сервис) | **per-node** | да |
| Fan-out независимых компонентов (каждый — свой бандл/репозиторий) | **per-node** | да (в пределах лимита) |
| Fan-out компонентов ОДНОЙ кодовой базы (растёт один репозиторий: каркас → модуль A → модуль B → общие тесты) | **per-group** (общий том) | нет → **сериализуется** внутри группы |
| Итеративная доводка (build → тест упал → правка → пере-тест) | per-node (повтор = новый узел) ИЛИ per-group для скорости | — |
| Экономия времени (узлы переиспользуют `node_modules`/build-cache) | **per-group** (том как кеш) | зависит |

Ключевой компромисс: **per-node = изоляция + параллелизм**; **per-group = общая
ФС + кеш, но сериализация** (параллельная запись в один том = конфликты).

### 1.3 Решение

- **Дефолт — per-node (свежий workspace), ephemeral, параллелится** в пределах
  класса конкуррентности. Совпадает с иммутабельностью артефактов, idempotent-retry
  и корректностью отката — это «правильный по построению» базис.
- **per-group (общий именованный том)** — явная **опция на уровне сборочной
  группы** (objective/fan-out), включается там, где компоненты образуют ОДНУ
  кодовую базу или нужен общий кеш; внутри группы исполнение **сериализуется**.
  Контейнер всё равно ephemeral на узел — просто монтирует общий том.
- **На первых этапах (Ф1–Ф6) — только per-node.** per-group вводим на Ф8
  (полный цикл спека→реализация), когда появятся реальные многокомпонентные
  кодовые базы и понадобится общий репозиторий/кеш. `SandboxRuntime` сразу
  проектируем так, чтобы том был параметром provision (per-group не требует
  переделки контейнерной модели).
- C (пул тёплых воркеров) и D (hosted API) — за горизонтом, интерфейс их не
  запрещает.

**Антиперегрузка на уровне модели:** ephemeral + жёсткий потолок параллельных
контейнеров (§5) — система никогда не держит больше N контейнеров, простой не
жрёт ресурсы, зависший агент убивается по таймауту.

## 2. Как система разговаривает с Docker

Три механизма:

1. **Docker CLI (`docker ...`) через subprocess.** Прецедент в репозитории —
   `mermaid_render` шеллит `mmdc` с graceful degradation. Зависимостей ноль,
   кросс-платформенно (Docker Desktop кладёт `docker` в PATH).
2. **`docker` Python SDK (docker-py).** Структурный контроль: стрим логов,
   `stats` (CPU/RAM), `exec`, события, аккуратный lifecycle. +зависимость.
3. **Docker Engine HTTP API напрямую.** Максимум контроля, максимум возни.

**Рекомендация:** **docker-py** как основной механизм — нам критичны стрим
транскрипта, `stats` для наглядности и надёжный `stop/kill`; на CLI это
парсинг текста. Зависимость объявляем **опциональной** (как `mmdc`/puppeteer):
нет Docker/SDK → harness-провайдеры деградируют, ядро и LLM-путь живут, CI
зелёный на stub. Абстракция ниже изолирует выбор.

### 2.1 Абстракция `SandboxRuntime` (инфраструктура)

Один интерфейс — много движков (Docker сейчас; позже Podman/remote/k8s/hosted):

```
class SandboxRuntime(Protocol):
    def provision(self, image: str, limits: ResourceLimits) -> SandboxHandle: ...
    def put_files(self, h: SandboxHandle, files: Mapping[str, bytes]) -> None: ...
    def exec(self, h, argv, *, env, timeout_s, on_log) -> ExecResult: ...   # стрим логов
    def stats(self, h) -> ResourceStats: ...                                 # CPU/RAM/диск
    def get_files(self, h, path) -> Mapping[str, bytes]: ...                 # harvest-by-convention
    def get_diff(self, h, repo_path) -> str | None: ...                      # harvest-by-diff
    def stop(self, h) -> None: ...                                           # graceful → kill
    def destroy(self, h) -> None: ...                                        # teardown
```

`DockerSandboxRuntime` — единственная реализация на первом этапе. `StubSandboxRuntime`
(без Docker) — для тестов: пишет фикстуры, имитирует фазы.

## 3. Жизненный цикл прогона ноды (фазы = наблюдаемые состояния)

Один лист-узел `executor: harness` проживает шесть фаз. Каждая — наблюдаемое
состояние `harness_runs.phase` (для live-ленты и провенанса):

```
queued ─► provisioning ─► seeding ─► running ─► harvesting ─► validating ─► done
   │            │            │          │           │            │
   │ (нет слота)│            │          │           │            └─ гейты build/test/lint
   │            │            │          │           └─ файлы по соглашению + git-дифф
   │            │            │          └─ агент работает, стрим транскрипта, бюджет тикает
   │            │            └─ копируем входные артефакты как файлы + git init (для diff)
   │            └─ docker run из образа адаптера + лимиты cgroup
   └─ ждём слот в классе конкуррентности harness
                                          (отмена/таймаут на любой фазе ─► stopped/partial/failed)
```

- `TaskRecord.status` остаётся **грубым** (`in_progress`), а тонкая фаза —
  в `harness_runs`. Так лента «В работе» (уже построена) показывает узлы-агенты
  без переделки, а детали — по клику.
- Чекпоинт pre-state снимается перед стартом узла (как сейчас) → откат-совместимо.

## 4. Образы

- **Базовый образ на адаптер** (например `povgen/harness-claude-code:<digest>`):
  агент + тулчейн (git, node, python, базовые build-инструменты). Версионируется,
  **пинится по digest** (воспроизводимость).
- **Кастомный образ** — пользователь может указать свой в настройках подключения
  (свой тулчейн/язык).
- **Pre-pull, не lazy-pull.** Тянуть GB-образ ПОСРЕДИ прогона = узел «висит»
  минуты. Образы тянем заранее в онбординге (§6) с прогрессом; перед прогоном
  лишь проверяем наличие.
- **Диск:** prune dangling после teardown; следим за свободным местом (guard);
  блоб-хранилище артефактов имеет бюджет (см. компаньон §7).

## 5. Ресурсы и защита от перегрузки (центральная тема)

Семь механизмов, многослойно:

1. **Отдельный класс конкуррентности harness.** LLM-шаги можно лить десятками;
   контейнер занимает CPU+RAM+диск. Поэтому **отдельный маленький семафор**
   (дефолт 1–2 параллельных контейнера), независимый от лимита LLM-шагов.
   Встраивается в существующий `ParallelWorkflowScheduler` как ресурс-класс.
2. **Per-container cgroup-лимиты** на каждом `docker run`: `--cpus`, `--memory`
   (+`--memory-swap`), `--pids-limit`, диск (tmpfs size / `--storage-opt`),
   `--ulimit`. Один агент не съедает хост.
3. **Бюджеты прогона** (мягкие, в нашем коде): wall-clock, max_tokens, max_steps,
   max_cost. Истёк wall-clock → форс `stop`→`kill`. Бюджеты — governance-лимиты
   ВНУТРИ системы, не «оценки-гарантии» пользователю.
4. **Очередь/бэкпрешер.** Нет слота → узел в статусе `queued` («ждёт слот»),
   а не штурмует хост. Видно в ленте/панели.
5. **Авто-ёмкость хоста.** Детектим cores/RAM → дефолтная конкуррентность и
   лимиты = f(хост). Не даём поставить 10 контейнеров на 8 ГБ. Показываем
   «ваша машина потянет N параллельно».
6. **Дисковая гигиена.** Ephemeral контейнеры + именованные тома; авто-prune;
   потолок суммарного блоб-хранилища; предупреждение при нехватке места.
7. **Деградация.** Docker недоступен/демон лёг → узлы-агенты падают явно с
   понятным сообщением (или, по политике, прогон встаёт на паузу на этих узлах),
   но система не рушится. Тесты — на stub.

Итог: при любой нагрузке держится не больше N контейнеров с потолками ресурсов,
зависшие убиваются по таймауту, остальное ждёт в очереди — хост предсказуем.

## 6. Установка и онбординг (от «чистой системы» до «агент работает»)

Самое уязвимое для UX. Поток первого запуска должен быть явным и наглядным, а не
«молча тянем 3 ГБ и первый узел висит 5 минут».

**Шаги (страница «Агенты/Harness» в настройках + индикатор готовности):**

1. **Проверка Docker.** При первом обращении к harness-фиче пробуем демон
   (`docker version`/ping). Нет → экран: «Для агентов нужен Docker. Установите
   Docker Desktop (Win/Mac) / engine (Linux), затем нажмите Проверить».
   Индикатор: `Docker: запущен / не найден / демон недоступен`.
2. **Подготовка образов.** Кнопка **«Подготовить агентов»** тянет образ(ы)
   адаптера с **прогрессом** (статус `образ готов / тянется 40% / ошибка`).
   Без этого шага реальный прогон не запускается (fail-loudly с подсказкой).
3. **Подключение harness.** Регистрируем connection: тип (адаптер), образ,
   дефолт-модель, креды (эфемерно), лимиты. Курируемые **дефолты из коробки** —
   чтобы после pull образа + ключа модели всё работало.
4. **Модель/креды.** Агенту нужен LLM (Claude Code → ключ Anthropic; Aider →
   любой). **Переиспользуем существующие LLM-настройки**/`secret_box`: harness
   берёт уже настроенную модель, не дублируем ввод ключей.
5. **Self-test.** Кнопка **«Проверить агента»** (зеркало «Проверить подключение»
   у LLM): тривиальный прогон в песочнице («создай hello.txt») → успех/латентность.
   Доказывает, что весь рантайм рабочий ДО реальной задачи.
6. **Калибровка ёмкости.** Детект cores/RAM → предложенные конкуррентность и
   лимиты (с возможностью переопределить).
7. **Кросс-платформа и деградация.** Docker Desktop (Win/Mac) / engine (Linux) —
   документируем. Без Docker система полностью работает на LLM-пути; агенты —
   аддитивная возможность.

**Принцип онбординга:** ни одной «тихой» долгой операции — pull образов, self-test
и проверка Docker всегда явные, с прогрессом и понятной ошибкой.

## 7. Безопасность рантайма

- **Изоляция:** контейнер; конфайнмент ФС — монтируем только песочницу/том, не
  хост; cgroup-лимиты; произвольный код только в контейнере.

### 7.1 Сеть/egress — анализ и решение (#5)

Полный запрет сети **ломает** кодинг-агентов: (а) агенту нужен LLM-эндпоинт (его
«мозг» — это сетевой вызов), (б) сборка тянет зависимости (pip/npm/apt),
(в) иногда git-fetch. Полный allow-all — риск утечки данных произвольному хосту.
Варианты:

1. **Allow-all** — удобно, небезопасно (эксфильтрация). Отвергаем.
2. **Deny + белый список** — запрет по умолчанию, разрешены: LLM-эндпоинт(ы) +
   пакетные реестры (pypi/npm/…) + git-хосты; список расширяется в настройках.
   Стандартный баланс.
3. **LLM через host-proxy** — агенту в контейнер пробрасываем loopback-прокси,
   который форвардит на настроенного провайдера **нашим** ключом. Контейнер
   **не видит реальный ключ** (усиливает правило «не храним/не отдаём секреты») и
   не может слать LLM-трафик на произвольный хост. Реестры всё равно по списку.

**Решение:** **deny-by-default + курируемый белый список** (LLM + реестры +
git), расширяемый пользователем — как старт. **host-proxy для LLM** — шаг
харднинга позже (убирает ключ из контейнера полностью). Полное отключение сети
оставляем как тумблер «максимальная изоляция» с явным предупреждением, что
большинство реальных агентов в этом режиме не работают. Документируем: список —
это поверхность доверия, держим узким.
- **Секреты:** правило «система не хранит секреты» соблюдаем — целевые токены
  подаются в контейнер **эфемерно** (env на время прогона, не персистим);
  фиксируем лишь факт «предоставлено» + несекретную заметку. Ключи
  harness-подключений — в `secret_box` (как LLM-ключи).
- **Эффекты только в песочнице:** наружу — только артефакты; push/deploy/внешние
  вызовы выключены на первом этапе (зарезервированы под явный gate позже).
- **Произвольный код — только в контейнере**, никогда в процессе API.

## 7bis. Образ как выходной артефакт (без Docker-in-Docker)

Часть выходных артефактов — **готовый Docker-образ**, который пользователь сможет
запустить. Чтобы его собрать/протестировать «изнутри» агента, наивно нужен Docker
внутри песочницы. Разбор вариантов:

| Подход | Что это | Вердикт |
|---|---|---|
| **DinD (Docker-in-Docker)** | внутри sandbox-контейнера крутится свой dockerd (`docker:dind`) | **Нет.** Требует `--privileged` → контейнер фактически может сбежать на хост, что **убивает весь смысл песочницы** для недоверенного кода агента. Плюс вложенный overlayfs, медленно, хрупко. |
| **DooD (mount /var/run/docker.sock)** | агент `docker build` бьёт в ДЕМОН ХОСТА | **Категорически нет.** Доступ к сокету хоста = root на хосте (монтирование ФС хоста, privileged-контейнеры). Худший вариант для произвольного кода. |
| **Daemonless-сборка (kaniko / buildah / BuildKit-rootless)** | сборка OCI-образа из Dockerfile **без демона и без `--privileged`**, в userspace; выход — tarball образа | **Да.** Сделано ровно для «безопасно собирать образы в CI/песочнице». |
| **Разделение ролей: агент пишет рецепт, система собирает** | агент отдаёт Dockerfile + контекст как файловый артефакт; отдельный доверенный шаг собирает образ | **Да, основной паттерн.** |

### Решение: агент не получает Docker; образ собирает доверенный шаг

1. **Агент** (узел `executor: harness`) производит **исходники + Dockerfile +
   build-контекст** как файловый бандл. Никакого доступа к Docker-демону/сокету
   у агента нет — он лишь пишет «рецепт».
2. **Сборка образа — отдельный доверенный шаг** (специальный `quality_gate`
   «docker-build» или выделенный build-узел): запускает **kaniko/buildah**
   (daemonless, без privileged, без сокета хоста) на Dockerfile+контексте агента.
   Выход — **OCI-образ как tarball** (`docker save`/OCI-layout) → это и есть
   артефакт-бандл, который пользователь делает `docker load` и запускает.
3. **Тест образа** — контролируемый прогон: поднимаем **уже собранный нами**
   (доверенный) образ в свежем sandbox-контейнере, выполняем smoke-тест/healthcheck,
   снимаем результат. Это запуск ИЗВЕСТНОГО образа нашим рантаймом, а не выдача
   агенту доступа к демону.

Так недоверенный агент **никогда не касается Docker-демона**, а реальный,
запускаемый образ всё равно собирается и проверяется. DinD/DooD не нужны.

**Почему это чисто:** граница доверия проходит между «агент пишет файлы»
(недоверенное, аудируемо) и «система собирает по фиксированной команде»
(доверенное). Сборщик (kaniko) и команда — наши; вход — только файлы.

**Когда DinD всё же оправдан:** если САМА задача требует от агента
оркестрировать контейнеры (например, поднять docker-compose из нескольких
сервисов и погонять интеграцию). Тогда — **rootless-движок** (sysbox-runtime или
rootless dockerd), **никогда** `--privileged`+сокет хоста. Это продвинутый
сценарий — откладываем; базовый «собрать и отдать образ» закрывается kaniko.

**Хранение:** image-tarball — это файловый бандл (см. компаньон §7): на диске под
workspace + указатель/манифест в `artifacts` (роли, размер, хеши, теги). SQLite
блобом не раздуваем; экспорт включает tarball.

**Влияние на план:** добавляется тип гейта «собрать-образ» (kaniko) и «прогнать
образ» (smoke) — это часть Ф5 (файловые артефакты + гейты/DoD). Базовый образ
сборщика (kaniko) — ещё один управляемый образ в онбординге (§6).

## 8. Наблюдаемость («наглядно»)

Рантайм обязан быть прозрачным на трёх уровнях:

1. **Системная панель «машинное отделение»** (новая, в настройках/статусе):
   - Docker: запущен/нет; версия.
   - Образы: готов / тянется / отсутствует (с прогрессом pull).
   - Слоты: `занято N / M` контейнеров; очередь harness-узлов.
   - Ёмкость хоста и текущая загрузка.
2. **Per-node live** (расширяет ленту «В работе»):
   - фаза (`provisioning→running→harvesting→validating`);
   - живой транскрипт (стрим stdout агента) + лог инструментов;
   - бюджет: токены/$/время vs лимит (прогресс-бар «приближается к лимиту»);
   - (опц.) ресурсы контейнера CPU/RAM из `stats`.
3. **Per-run результат:**
   - дерево произведённых файлов + git-дифф;
   - результаты гейтов (build/test/lint — pass/fail с логом);
   - финальный статус, длительность, потрачено бюджета.
4. **Провенанс L3/L4:** digest образа, адаптер+версия, brief, seed, транскрипт,
   дифф, usage — тем же паттерном, что methodology-trace.

Governance денег/времени показываем как **внутренние лимиты прогона**, а не как
оценки-гарантии заказчику (правило проекта).

## 9. Отмена, таймауты, сбои

- **Отмена:** `CancellationToken` (форс уже есть) → `SandboxRuntime.stop`
  (graceful) → `kill`/`docker stop`. Частичный результат сохраняем как `partial`.
- **Таймаут:** wall-clock прогона → тот же путь стоп→kill.
- **Сбой гейтов / агент сделал не то:** узел `failed` с причиной → штатный retry
  (модель попыток есть) или эскалация; машинный DoD ловит «сделал не то».
- **Docker лёг посреди прогона:** узел `failed` с понятной причиной, прогон
  продолжается на остальном (LLM-узлы не затронуты).

## 11. Резолюция «какой harness» при выборе только шаблоном

Шаблон говорит лишь «`executor: harness`» (провайдер-агностично, как `executor: llm`
не называет модель). Конкретный исполнитель резолвится из настроек:

- **Первый этап:** один **дефолтный harness-connection** (как сейчас дефолтный
  execution-provider = `stub`). Все harness-узлы идут через него.
- **Позже (опц.):** назначение «класс задачи → harness» (зеркало «класс → модель»)
  — без правки шаблонов. Per-node override решено НЕ делать.
- Не настроен/нет образа → fail-loudly с подсказкой («Подготовьте агента в
  настройках»).

## 11bis. Адаптеры: Claude Code vs Aider — сравнение и выбор (#3)

Оба ложатся за ОДИН контракт `HarnessProvider` (перевод `HarnessRunSpec` →
вызов CLI в контейнере + парс результата). Общая обвязка (песочница, посев,
рендер brief, harvest, teardown) — одна на всех. Поэтому **поддержать оба —
небольшая доп. работа**: различия не текут в ядро, адаптер маленький.

| Ось | Claude Code (`claude` CLI / agent-sdk, headless) | Aider (CLI) |
|---|---|---|
| Автономность/планирование | Высокая: многошаговый агент, под-агенты, инструменты | Средняя: сфокусированный edit-цикл по файлам |
| Модели | Только Claude (Anthropic) | Любые (litellm: Claude/GPT/локальные) → гибкость цены |
| Git | через инструменты | **нативно** — коммит на каждую правку (идеально для diff-harvest) |
| Headless/скриптинг | зрелый (`claude -p`/SDK) | зрелый (создан под скриптинг: `--message --yes`) |
| Силён в | сложное, многофайловое, «построй X» с разведкой | точные правки по хорошей спеке, контроль стоимости |
| У нас уже есть | да (`claude_subscription`/`claude_sdk`) | нет |
| Стоимость | по цене Claude | гибкая (можно дешевле) |

**Разница по сути:** Claude Code — тяжёлый автономный «строитель» (берёт спеку и
делает многошагово), Aider — точный, модель-гибкий, git-нативный «редактор».
Они **дополняют**, а не конкурируют.

**Решение:** поддержать **оба** как курируемые подключения, выбор — за
пользователем (как вы и предложили). **Дефолт — Claude Code** (максимальная
автономность под «собери компонент по спеке» + уже интегрирован). **Aider** —
модель-/цена-гибкая альтернатива и самый чистый diff-harvest. Плюс
**generic command-harness** (запуск произвольного агент-CLI) как escape hatch.

**Порядок реализации (Ф7):** контракт и обвязка — раньше (Ф1–Ф2). Первым
**реальным** адаптером логично сделать **Aider** — его «коммит-на-правку»
даёт тривиальный, наглядный harvest-by-diff (хорошая проверка всей сборки
результата дешёвыми моделями), затем **Claude Code** (мощнее, переиспользует
нашу интеграцию). Оба — взаимозаменяемы за `HarnessProvider`.

## 12. Фазы реализации (рантайм-ориентированные)

Дизайн-доки (этот + компаньон) = **Ф0**. Дальше — раз Docker важен, рантайм
проектируется заранее, но кодим послойно с зелёным CI на каждом шаге:

- **Ф1 — контракт + диспетч + stub-рантайм (без Docker).** `executor: harness`,
  `harness/protocol.py`, `harness/registry.py`, `StubSandboxRuntime` + фикстуры,
  рендер brief, harvest-by-convention, диспетч в `execute_task`, дефолтный
  harness-connection. Сквозной зелёный тест на стабе. Downstream не трогаем.
- **Ф2 — `SandboxRuntime` + DockerSandboxRuntime (реальная песочница).**
  lifecycle (§3), cgroup-лимиты, стрим логов, stop/kill, egress-deny. Образ под
  первый адаптер. Тесты lifecycle на стаб-движке; Docker-путь — за флагом.
- **Ф3 — класс конкуррентности + бюджеты + очередь.** Семафор harness,
  enforcement лимитов/таймаута, статус `queued`, авто-ёмкость хоста.
- **Ф4 — установка/онбординг.** Проверка Docker, pre-pull с прогрессом,
  self-test, калибровка ёмкости, страница настроек подключений.
- **Ф5 — файловые артефакты + гейты (DoD).** Блоб-хранилище + манифест,
  `quality_gate` build/test/lint в песочнице, машинный DoD.
- **Ф6 — наблюдаемость.** Панель «машинное отделение», per-node live (фаза/
  транскрипт/бюджет/ресурсы), per-run результат (файлы/дифф/гейты), провенанс L3/L4.
- **Ф7 — первые реальные адаптеры (≥2)** за `HarnessProvider` + матрица
  возможностей; generic command-harness как escape hatch.
- **Ф8 — полный цикл «спека→реализация»** на базе `component_build_spec`
  (fan-out, B-lite общий том) + раздел в `ARCHITECTURE.md`.

Каждая фаза — отдельный коммит, ruff + pytest + (UI) build + рестарт.

## 13. Журнал решений (рантайм)

Решено (2026-06-07):
1. **Механизм Docker — docker-py** (опциональная зависимость; деградация без
   Docker; всё за `SandboxRuntime`).
2. **Модель исполнения — контейнер ВСЕГДА ephemeral; область workspace per-node
   по умолчанию**, per-group (общий том, сериализация) — опция на сборочную
   группу, вводится на Ф8 (§1.1–1.3).
3. **Адаптеры — поддерживаем оба** (Claude Code + Aider), выбор пользователя;
   дефолт Claude Code; первым реализуем Aider как референс harvest; generic
   command-harness — escape hatch (§11bis).
5. **Egress — deny-by-default + курируемый белый список** (LLM + реестры + git),
   расширяемый; host-proxy для LLM — харднинг позже; полный офлайн — опциональный
   тумблер с предупреждением (§7.1).
6. **Образ как артефакт — без DinD/DooD**: агент пишет Dockerfile+контекст,
   доверенный шаг собирает kaniko/buildah (daemonless), тест — прогон собранного
   образа нами; tarball = бандл-артефакт (§7bis).

Отложено:
4. **Дефолтные лимиты** (конкуррентность, CPU/RAM/диск на контейнер, wall-clock,
   бюджет $) — числа подберём при реализации рантайма (Ф2–Ф3), значения
   настраиваемые в UI; решение по конкретным дефолтам — позже.

Открытое (по ходу):
- Нужен ли rootless-DinD для задач-оркестраторов (compose) — отдельный сценарий,
  за горизонтом; базовый «собрать образ» закрыт kaniko.

Реализовано (2026-06-08, Ф5c — гейты/DoD):
- `HarnessGate`/`GateResult` в `harness/protocol.py`; `gates` в `HarnessRunSpec`
  и `HarnessRunResult`. `harness/gates.py::run_gates` прогоняет команды-проверки
  в той же песочнице (исполняет ВСЕ для полноты отчёта; `passed = exit 0 и не
  таймаут`). `CommandHarnessProvider` гонит гейты ПОСЛЕ агента и ДО сбора —
  провал любого = `status=failed` без сбора артефакта (DoD не достигнут → штатный
  retry). Источник гейтов — шаблон: `harness_gates` (домен `HarnessGateSpec`),
  пробрасывается `execute_task → HarnessExecutionService.produce_artifact → spec`.
- Сборка образа (kaniko/buildah) — частный случай команды-гейта; отдельного типа
  не вводим, фреймворк гейтов её покрывает.
- Stub-harness гейты не исполняет (фикстура-выход); объявление гейтов на узле
  безопасно — реальные адаптеры (Ф7) их прогонят.

Реализовано (2026-06-08, Ф6a — «машинное отделение», живой статус рантайма):
- `HarnessExecutionService.runtime_status()` → `HarnessRuntimeStatus` (провайдер,
  слоты класса конкуррентности + очередь, накопленный расход, лимиты прогона,
  причина превышения кумулятивного потолка). Делегируется из
  `ExecutionService.harness_runtime_status()` — тот же экземпляр, что исполняет
  узлы, поэтому занятость/расход живые.
- Эндпоинт `GET /api/harness/runtime` (отдельно от `/status`: подготовка
  Docker/образа vs. текущая загрузка). `app.state.execution_service` подвязан.
- Деньги/время — внутренние governance-лимиты, не оценки заказчику.
- Осталось по Ф6: per-node провенанс L3/L4 (транскрипт/brief/гейты/usage),
  per-run результат (дерево файлов/дифф), и UI (панель + drill-down).

Реализовано (2026-06-08, Ф6b — провенанс прогона узла-агента L3/L4):
- `HarnessOutcome.gates` (результаты гейтов доходят до сервиса) +
  `HarnessOutcome.trace_payload()` — самодостаточная сводка «как получен
  артефакт»: адаптер, model, output_kind, brief, транскрипт, гейты, расход.
- Новое поле `ArtifactMetadata.harness_trace` (зеркало `methodology_trace`):
  round-trip в `sqlite_runtime` (known/from/to payload). Заполняется в
  `execute_task` для обоих выходов — структурного и файлового бандла.
- `WorkspaceQueryService.task_harness_trace` + `GET /api/projects/{id}/tasks/
  {task_id}/harness-trace` (тем же паттерном, что methodology-trace).
- Stub гейты не исполняет → `gates=[]`; usage не выдумываем (None, если
  провайдер не дал данных).
- Осталось по Ф6: per-run дерево файлов/дифф (частично — бандл уже хранит
  файлы+манифест) и UI (панель «машинное отделение» + drill-down провенанса).
