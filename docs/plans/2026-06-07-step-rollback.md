# Ролбек шага: откат к состоянию ДО выполнения выбранного шага

Статус: **реализовано** (Ф1–Ф7). Семантика выбрана заказчиком: **только
зависимые** (хирургический откат), **авто-отмена активного прогона +
ожидание**, артефакты **архивируются** (не удаляются).

Карта реализации:
- Ф1–Ф2 (домен/инфра): `domain/rollback.py` (StepCheckpoint, RollbackRecord,
  RollbackResult, ProjectLock), `StateEvent.task_id`/`rolled_back_by`, команда
  задачи `rollback_reset`, `position_from_primitive`; в `sqlite_runtime.py` —
  таблицы `step_checkpoints`/`rollbacks`/`project_locks`, колонки `task_id`/
  `rolled_back_by`, методы захвата чекпоинта, архивации, замка.
- Ф3 (движок): `rollback_graph.py` (замыкание зависимостей по write∩read),
  `state_patch_codec.py` (декод патчей + реплей слоёв), `rollback_service.py`
  (реконструкция из чекпоинта самого раннего откаченного шага).
- Ф4 (шлюз/конкуррентность): `project_lock.py` (`ensure_project_unlocked`),
  `rollback_coordinator.py` (замок + авто-отмена прогона + откат + снятие).
- Ф5 (проекции/API): `RollbackPreviewView`/`ProjectRollbackHistoryView`,
  `WorkspaceQueryService.rollback_preview`/`rollback_history`, эндпоинты
  `GET /rollback/preview`, `GET /rollback/history`, `POST /commands/rollback`;
  guard submit-эндпоинтов решений.
- Ф6 (UI): кнопка «↶ Откатить» на завершённом листовом шаге графа, диалог
  превью `RollbackPreviewModal` (инвалидируемые шаги + архивируемые артефакты),
  секция «История откатов».
- Ф7: эта запись + раздел в `ARCHITECTURE.md`.

## 1. Потребность

Дать возможность выбрать уже выполненный шаг X и откатить проект к состоянию,
которое было **до** выполнения X. При этом:
- инвалидируются X и все шаги, **зависящие** от X (транзитивно);
- артефакты откаченных шагов **архивируются** (остаются в истории/аудите,
  файлы на диске сохраняются), а не удаляются;
- независимые шаги, выполненные после X, **сохраняются**;
- система корректно реагирует на конкуррентные запросы: во время ролбека
  останавливается и не даёт запускать новое; активный прогон гасится.

Это системная фича, а не костыль: опирается на уже существующие провенанс,
событийный лог состояния и механизм отмены.

---

## 2. Модель состояния (на чём строим)

- **Знания и процесс** (`knowledge`, `process`) — событийные: снимок-последнего
  (`knowledge_snapshots`/`process_snapshots`) + append-only лог патчей
  `state_events` (версия + `patch_type` + `payload_json`). То есть состояние
  восстановимо реплеем патчей.
- **Проекции** (`tasks`, `artifacts`, `decisions`, `execution_runs`,
  `validation_runs`, `context_manifests`, `llm_usage`, `checkpoint_sessions`) —
  мутабельные, но с провенансом: `artifacts.created_by_task_id`,
  `*.task_id`, `decisions.source_task_id`.
- **Фактические чтения шага** — в `context_manifests` + `context_manifest_items`
  (`source_ref` вида `artifact:<id>` / `knowledge:<...>`, плюс
  `used_position_ids_json`). То есть для каждого шага известно, что он реально
  прочитал.
- **Контракты** — `template.inputs` (требуемые артефакты/readiness/gaps/поля) и
  `template.effects` (readiness.set, gaps.close) задают, что шаг требует и что
  отдаёт.
- **Конкуррентность уже есть**: per-workspace write-coordinator
  (`@_serialized_write`), рантайм-прогон (`workflow_runs` + `cancel_requested`),
  `CancellationToken` + форсированная отмена (`cancel_run`).

## 3. Граф зависимостей шага (что считать зависимым)

Зависимость **звуковая** (надмножество реального потока данных), а не эвристика.
Для каждого выполненного шага считаем:

**write-set(X)** — что шаг произвёл/изменил:
- артефакты с `created_by_task_id == X` (роли + id);
- из `state_events` шага X (после доработки — с `task_id`): добавленные
  knowledge-позиции, выставленные readiness-измерения, закрытые/открытые gaps,
  изменённые поля состояния.

**read-set(Y)** — что шаг реально прочитал/потребовал:
- фактические чтения из `context_manifests` шага Y: входные артефакты
  (`source_ref=artifact:<id>`) и knowledge-позиции (`used_position_ids`);
- контрактные требования `template.inputs` шага Y (артефакты/readiness/gaps),
  сопоставленные с тем, кто их **последним отдал до Y**.

**Ребро X → Y**, если `write-set(X) ∩ read-set(Y) ≠ ∅` и X выполнен раньше Y.
**Откатываемое множество R = X ∪ транзитивные потомки X** в этом графе.

Особые узлы:
- **fan-out инстансы** наследуют зависимость родителя-веера; откат веера
  откатывает все его инстансы (и наоборот — откат источника веера откатывает
  веер).
- **композиты** откатываются, если откачен любой их обязательный ребёнок
  (их «готовность» зависела от детей).

Граничные случаи фиксируем тестами; при сомнении множество R **расширяем**
(консервативно), а не сужаем — лучше откатить лишний зависимый шаг, чем
оставить несогласованный.

## 4. Реконструкция глобального состояния без вклада R

Просто восстановить один блоб-чекпоинт нельзя — это откатило бы и независимые
шаги. Поэтому реконструируем знания/процесс реплеем переживших патчей:

1. **Чекпоинт на шаг.** Перед выполнением каждого листового шага (единая точка —
   вход `execute_task`) снимаем `step_checkpoint`: блобы `knowledge`+`process` и
   их версии, `objective_ref`, монотонный `seq`. Это «состояние ДО шага».
2. `earliest` = откатываемый шаг из R с минимальным `seq`.
3. Берём `base = step_checkpoint(earliest)` (состояние прямо перед самым ранним
   откаченным шагом).
4. **Реплей**: применяем по порядку `seq` все `state_events` с `seq > earliest.seq`,
   у которых `task_id ∉ R` (и события без `task_id` — пользовательские/
   глобальные, например `activate_next_objective` — сохраняем). Каждый патч
   десериализуется из `payload_json` и применяется чистой функцией
   `apply_*_patch`.
5. Результат пишем как новый снимок (свежая версия), добавляем
   `state_event` типа `rollback` — лог остаётся честным append-only.

Это корректно, потому что пережившие шаги по определению независимы от R: их
патчи (set readiness / add position / close gap) — абсолютные/аддитивные дельты,
переигрываются поверх базы без вклада R без конфликтов.

Требует: (а) `step_checkpoints`; (б) `state_events.task_id`; (в) реестр
десериализации патчей (`patch_type → класс.from_primitive`).

## 5. Алгоритм ролбека (атомарно, под write-coordinator)

`RollbackService.rollback_to(workspace, target_task_id, actor, reason)`:

1. **Шлюз вкл.**: ставим проектный замок `rollback` (см. раздел 6).
2. **Гасим прогон**: если активен `workflow_run` — форсированная отмена
   (`cancel_run`) + дождаться оседания.
3. Под `@_serialized_write` (одна транзакция):
   - вычисляем R (раздел 3);
   - реконструируем `knowledge`/`process` (раздел 4);
   - **архивируем артефакты** R: помечаем `rolled_back_by` = rollback_id (не
     удаляем; уходят из активных проекций, остаются в истории; файлы целы);
   - **архивируем побочные записи** R: `decisions` (по `source_task_id`),
     `validation_runs`, `execution_runs`, `checkpoint_sessions`, манифесты,
     usage — помечаем тем же `rolled_back_by`;
   - **сбрасываем задачи** R новой доменной командой `rollback_reset`:
     терминальный статус → начальный (`initial_task_status`), `attempt+1`,
     ошибка очищена; fan-out инстансы → `obsolete` (будут заново развёрнуты);
   - пишем аудит в `rollbacks` (target, R, кто/когда/почему) + `state_event`
     `rollback`;
   - **реквизиты пользователя не трогаем** — это входы, а не выходы шага.
4. **Шлюз выкл.** Планировщик при следующем `plan`/`expand_graph` пере-оценит
   допустимость: X снова `ready`, проект продолжается с него. Повторный прогон
   создаст новые артефакты (EC4 — иммутабельность; коррекция = новый артефакт).

## 6. Конкуррентность и шлюз

Чтобы система «останавливалась и не давала запускать», вводим **проектный замок**
`project_locks(project_id PK, kind, holder, acquired_at)` (kind=`rollback`).

- Пока замок держится, отказывают с понятной причиной (HTTP 409):
  `run_next`, `run-until-blocked`, `activate_next_objective`, submit-decision,
  retry-задачи, повторный ролбек.
- Активный прогон при старте ролбека **форсированно отменяется** (механизм уже
  есть) и дожидается оседания — выбор заказчика.
- Сам ролбек выполняется под per-workspace write-coordinator → атомарен, без
  чередования записей.
- Идемпотентность: откат к шагу, который уже не выполнен (или к началу), —
  no-op с понятным сообщением.
- Сбой посреди ролбека: всё в одной транзакции → откат БД-транзакции, замок
  снимается в `finally`; состояние не «полу-откачено».

## 7. Новая инфраструктура

Таблицы/колонки (миграции `_ensure_*`, обратносовместимо):
- `step_checkpoints(checkpoint_id, project_id, task_id, attempt, seq, knowledge_json, knowledge_version, process_json, process_version, objective_ref, created_at)`;
- `state_events.task_id TEXT NULL` (провенанс патча);
- `artifacts.rolled_back_by TEXT NULL` (архив-флаг; NULL = активен);
- аналогичный `rolled_back_by` на `decisions` (и фильтрация в проекциях);
- `rollbacks(rollback_id, project_id, target_task_id, target_seq, affected_json, actor, reason, created_at)` (аудит);
- `project_locks(project_id, kind, holder, acquired_at)`.

Код:
- домен: команда `rollback_reset` в `apply_task_command` (терминальный →
  начальный, attempt+1); модели `RollbackPlan`/`RollbackResult`;
- реестр десериализации патчей (`state_patch_codec`);
- `application/rollback_service.py` — оркестратор (граф R, реконструкция,
  архивация, шлюз);
- проекции (`workspace_query_service`) — везде фильтр `rolled_back_by IS NULL`
  для активных артефактов/решений; отдельная вьюха «архив отката»;
- API: `POST /projects/:id/rollback {target_task_id}` + `GET .../rollback/preview?target_task_id=` (показать R до подтверждения);
- guard во всех мутационных командах (`project_locks`).

## 8. UX/UI

- На шаге (L3/L4 граф задач или таймлайн) у завершённого шага — действие
  «Откатить к состоянию до этого шага».
- **Превью** перед подтверждением: список шагов, которые будут инвалидированы
  (R), и артефактов, которые уйдут в архив. Без сюрпризов.
- Во время ролбека — индикатор «идёт откат», действия запуска заблокированы.
- После — X снова готов; архив доступен отдельным разделом (история).

## 9. Фазы реализации

- **Ф1 — чекпоинты шага + провенанс патчей.** `step_checkpoints` (снимок на
  входе `execute_task`); `state_events.task_id` (тегирование патчей текущим
  шагом через контекст исполнения); реестр десериализации патчей. Тесты:
  чекпоинт снимается, патчи реплеятся обратно в идентичное состояние.
- **Ф2 — граф зависимостей.** Вычисление write-set/read-set и транзитивного R
  из артефактов + `context_manifests` + контрактов; обработка fan-out/композитов.
  Чистая функция + тесты на разных топологиях.
- **Ф3 — движок ролбека.** Реконструкция состояния (реплей переживших),
  архивация артефактов/решений/прогонов, `rollback_reset` задач, аудит. Тесты:
  откат листа, цепочки, ветки с независимым соседом (сосед выживает).
- **Ф4 — шлюз и конкуррентность.** `project_locks`; авто-отмена активного
  прогона + ожидание; отказ мутаций под замком; идемпотентность. Тесты на гонки.
- **Ф5 — проекции и API.** Фильтр `rolled_back_by` в проекциях; preview + execute
  эндпоинты; вьюха архива. Тесты API.
- **Ф6 — UI.** Действие + превью + индикатор + раздел архива. npm build.
- **Ф7 — документация.** ARCHITECTURE.md + спеки.

Каждая фаза: registry validate + pytest + ruff + (UI) npm build + перезапуск.

## 10. Риски и как снимаем

| Риск | Снятие |
|---|---|
| Пропущенная неявная зависимость (Y тайно зависел от X) → несогласованность | read-set = фактические чтения из `context_manifests` (полный список того, что видел шаг) ∪ контрактные `requires`. При сомнении R расширяем. |
| Реплей патчей восстановит состояние неверно | Патчи — абсолютные/аддитивные дельты, применяются чистой функцией; Ф1-тест: реплей лога даёт идентичный снимок (golden). |
| Десериализация патчей неполна | Реестр кодеков покрыт тестами на каждый тип патча; неизвестный тип → явная ошибка, ролбек откатывается (транзакция), не «тихо». |
| Гонки во время ролбека | `project_locks` + write-coordinator + авто-отмена прогона; все мутации проверяют замок. |
| Версии состояния после реконструкции разъезжаются | После реплея пишем свежую версию + событие `rollback`; версии монотонны. |
| Раздувание `step_checkpoints` | Блоб на шаг; для PoV-масштаба мало. При нужде — прунинг старых чекпоинтов или хранение версий + реплей с нуля. |
| Кросс-objective откат (в ТЗ из архитектуры) | Чекпоинт хранит `objective_ref`; восстанавливаем и его. Большой радиус — в превью видно. |
