# Доработка: оценка реализуемости через каталог умений

Статус: проект (design), к реализации после согласования.
Отталкивается от: PR #14 (оценка реализуемости + «агенты» + Слой 2), уже влитого
в `integration/all-merges` как базовая версия.

---

## 1. Зачем это нужно (потребность)

Мы делаем ТЗ. Часть того, что в нём описано, мы реально можем построить
(ИИ-конвейером), часть — нет. Нам нужно:

1. честно понять, что мы **можем** сделать;
2. честно понять, что мы **не можем** сделать, и почему;
3. чисто разделить одно от другого и передать «можем» дальше — на реализацию.

Главное ограничение: строит ИИ, а он переоценивает себя и выдумывает. Если по
умолчанию считать «сделаем всё, что выглядит нормально» — мы провалимся. Значит
фильтр реализуемости — это в первую очередь **защита от собственного оптимизма
модели**, и только во вторую — про удобство.

Обратная сторона: слишком узкий список того, что мы «умеем», режет половину
запросов, которые мы на самом деле потянули бы. Поэтому список умений должен
**расти** от реальных запросов — безопасно, не возвращая «по умолчанию да».

## 2. Термины

Заменяем «агентов» на понятные слова. «Агент» обещает автономного исполнителя —
а на деле это контракт того, что мы умеем. Честное имя:

| Термин | Что это |
|---|---|
| **Умение** | одна проверенная вещь, которую мы реально умеем реализовать (на чём, что нужно, в каких пределах). Объект реестра. |
| **Каталог умений** | весь набор умений. |
| **Зрелость умения** | **надёжное** (подтверждено сдачами) или **пробное** (думаем, что можем, но ещё не доказали). |
| **Пределы умения** | до какого уровня нагрузки / надёжности / точности / объёма умение даёт гарантию. |
| **Пробел в умениях** | запрос, который ни одно умение не закрывает; кандидат на новое умение (раньше я называл его «кандидат» — это слово ни о чём не говорит). Для бизнеса — «зона роста». |
| **Оценка реализуемости** | шаг, который раскладывает требования по вердиктам. |
| **Вердикт** | по каждому требованию: *сделаем / сделаем с урезанием / пробел в умениях / не сделаем*. |
| **Закрывается умением** | связь «требование → умение» (с версией умения). |
| **Реквизиты** | раздел и канал для требуемых от пользователя входных данных (доступ, файл, настройка, значение). Не приговор реализуемости, а отдельная просьба. Это домашний раздел этапа «Реализация». |
| **Направление реализации** | backend / интерфейс / данные / интеграции / ML — для вопроса «кто строит». Вторично, нужно только на этапе сборки. |

### Решения по терминам (итог обсуждения с заказчиком)

- Раздел требуемых от пользователя данных называется **«Реквизиты»**.
- Оценка «что можем / что не можем» — это **отдельный артефакт** (не пометки на
  ТЗ). ТЗ показывает требования заказчика и их источники; отдельный артефакт
  реализуемости, опираясь на эти требования, описывает, что мы берём и что нет.
- Статусы в этом артефакте — нейтральные: **Реализуемо / Частично реализуемо /
  Не реализуемо** (плюс «требует данных» решается разделом «Реквизиты», а не
  статусом).
- Внутренние имена в коде остаются английскими; пользователю наружу — только
  статусы и «Реквизиты».

Переименования относительно PR #14:
- вид реестра `agent_capability` → **`capability`** (умение);
- `executor: agent` + `agent` → **`executor: llm`** + **`capability_ref`** (привязка контракта);
- «роль агента» → **направление реализации** (отдельный, поздний вопрос).

## 3. Принципы (на них держится всё остальное)

1. **По умолчанию — «не сделаем / не уверены». «Сделаем» надо доказать.** Бремя
   доказательства на «да». Это переворачивает умолчание в безопасную сторону.
2. **Гарантию дают не модель, а три человеческие опоры:** проверенный людьми
   каталог умений, заданные пределы, подтверждение человеком спорных случаев.
   Модель только сопоставляет и предлагает — она не имеет права сама сказать
   «сделаем».
3. **Ничего не теряем молча.** Непокрытое не выбрасывается, а становится
   пробелом в умениях (зоной роста). Невозможное и условия — уходят в уже
   существующие каналы: пробелы, вопросы-уточнения, эскалации, решения.
4. **Нехватка данных — это не «не можем».** Это отдельный запрос пользователю.
5. **Каталог растёт безопасно.** Охват добавляем там, где это выводимо без риска
   (близость к проверенному, разбор на известные части); всё остальное — через
   человека.

## 4. Из чего состоит каталог умений (модель данных)

### 4.1 Умение (объект реестра, `capability`)

Один небольшой YAML на умение (или семейство умений с чёткими границами):

```
kind: capability
id: capability.backend.crud_service
version: 1.0.0
title: Типовой CRUD-сервис над реляционной базой
build_track: backend            # направление реализации (опционально)
maturity: reliable              # reliable | trial
tech: [FastAPI, PostgreSQL]
prerequisites:                  # что нужно на вход → может стать запросом данных
  - Описание сущностей и их полей
limits:                         # пределы гарантии
  scale: "до ~50 сущностей"
  reliability: "обычная доступность, без жёсткого SLA"
  precision: "не реального времени"
  volume: "до ~100 тыс. записей на сущность"
boundaries:                     # для семейства — что входит / что точно нет
  in: ["создание/чтение/обновление/удаление", "простые фильтры"]
  out: ["сложная аналитика", "распределённые транзакции"]
cannot:                         # явные запреты
  - Юридически значимый биллинг без аттестованной системы
```

Ключевое отличие от PR #14: добавлены **пределы** и **границы** — именно они
ловят «слишком сложное / слишком надёжное / слишком большое», чего сейчас нет.

### 4.2 Данные проекта (не реестр, как пробелы/решения)

- **Вердикт реализуемости** на требование: ссылка на требование, состояние
  (4 значения), `covered_by` (умение@версия | пусто), ссылка на причину
  (пробел/ограничение/предел), уверенность, при урезании — что урезано, список
  нужных данных.
- **Пробел в умениях**: что просили, почему не нашли совпадения, черновик
  будущего умения (для простого добавления), близость к существующему умению,
  статус (открыт / повышен / отклонён).
- **Запрос данных**: что нужно, тип (доступ / файл / настройка / значение),
  статус (запрошено / получено), к каким требованиям относится.

## 5. Поток оценки реализуемости

Вход: требования в границах охвата + каталог умений + уже собранные факты
проекта (ограничения, пробелы, решения, подтверждённое заказчиком).

По каждому требованию:

1. **Сопоставление с умением.** Модель не решает «можем ли мы это» с нуля (соврёт
   «да»), а ищет совпадение с конкретным умением в каталоге — или честно
   признаёт, что совпадения нет.
2. **Проверка пределов.** Даже знакомое умение может не подойти, если от него
   хотят больше, чем гарантируют пределы (надёжность/точность/объём).
3. **Проверка нужных данных.** Нехватка доступа/данных → создаём **запрос
   данных**, но это НЕ понижает вердикт (это просьба, а не приговор).
4. **Вердикт:**

| Вердикт | Когда | Куда дальше |
|---|---|---|
| **Сделаем** | совпало с надёжным умением, пределы соблюдены, доказано | на реализацию |
| **Сделаем с урезанием** | совпало с пробным умением, либо хотят больше пределов, но есть приемлемый сокращённый вариант | на реализацию в урезанном виде (явно) |
| **Пробел в умениях** | совпадения нет, но возможно добавить (см. §6) | к человеку / в зону роста |
| **Не сделаем** | явный запрет, либо пределы превышены без приемлемого сокращения | фиксируем как ограничение / промышленный этап |

### Защита от выдумывания

- На каждое «сделаем» — **доказательство**: ссылка на конкретное умение +
  подтверждение, что пределы не превышены. Нет доказательства → «не уверены».
- **Второй проход наоборот**: модель отдельно ищет, **почему НЕ получится**. Что
  устояло — то и считаем выполнимым.
- Всё пробное и спорное — **к человеку** через существующий механизм решений с
  ответственным.

## 6. Как растёт каталог (закрываем пробелы безопасно)

Пробел в умениях — это не «нет», а заявка на рост. Охват добавляем двумя
безопасными путями + человеком:

1. **Близость к проверенному.** Если запрос — малый шаг от надёжного умения (та
   же технология, тот же шаблон), система предлагает добавить его как **пробное**
   умение, заранее подготовив черновик. Человеку остаётся проверить и принять.
2. **Разбор на части.** Если запрос = известное + маленький новый кусочек,
   известные части делаем сразу, а новый кусочек помечаем пробелом. Так из «нет»
   получается «80% сделаем, 20% — на оценку».
3. **По-настоящему новое** — к человеку: добавлять умение или нет.

### Жизненный путь умения

```
пробел в умениях → (решение добавить) → пробное умение → (N успешных сдач) → надёжное умение
                                              ↑ используется с осторожностью, результат помечен
        проваленные сдачи → понижение/удаление
```

Двигатель — **обратная связь от реальных сдач**: успешно сдали пробное несколько
раз → система предлагает повысить до надёжного; провалили → понижаем. Каталог
самокорректируется по фактам, а не по мнению.

### Простые способы расширения (требование пользователя)

- умение — короткий файл; пробел уже готовит черновик умения;
- умение-семейство покрывает много вариантов (но с жёсткими границами `boundaries`);
- разовый посев каталога из того, что мы уже реально сдавали в прошлых проектах.

## 7. Запрос данных у пользователя (механизм + UX/UI)

### 7.1 Идея

Доступ, файлы, настройки и значения — это не повод сказать «не можем». Это
**просьба к заказчику**, отдельная от вопросов-уточнений (вопрос — «как решим?»,
запрос данных — «дайте то-то»). Пока данные не получены, требование держится в
состоянии «сделаем, как получим данные» — это не блокировка всего прогона.

### 7.2 Принцип подачи: пакетом, а не по одному

Конвейер не останавливается на каждом запросе. Запросы **накапливаются** и
показываются пользователю пачкой: «вот что нужно, чтобы доделать вот это». Так
человек закрывает всё за один заход, а не дёргается по мелочам. Это совпадает с
уже принятой в проекте моделью вовлечения (единый экран открытых решений).

### 7.3 Где в интерфейсе

Запросы данных — это третий вид «ждёт вас», рядом с уже существующими вопросами и
решениями:

- **Уровень L1 (менеджер):** на проекте — счётчик-бейдж «нужно предоставить: N».
  Простой список, без технических деталей.
- **Отдельный раздел «Нужно от вас»** (подвкладка рядом с «Решения»), сгруппирован
  по тому, что разблокирует: «Чтобы сделать интеграцию с 1С, нужно: …».

### 7.4 Как выглядит один запрос

Карточка:
- **Что нужно** — коротко («Доступ к тестовому контуру 1С», «Файл с форматом
  выгрузки», «Значение тайм-аута»).
- **Зачем** — какое требование от этого зависит (ссылка на пункт ТЗ).
- **Тип и действие прямо в карточке:**
  - файл → загрузка (используем существующий механизм вложений);
  - значение/настройка → поле ввода;
  - доступ → отметка «предоставлено» + поле для ссылки/места доступа
    (сами секреты/токены в системе не храним — это на стороне пользователя);
  - подтверждение → переключатель «да/нет».
- **Состояние** — запрошено / получено.

### 7.5 Что происходит после

Как только данные получены — зависящее требование **переоценивается**: его
вердикт может перейти из «с урезанием/пробел» в «сделаем», и оно уходит на
реализацию. Пользователь видит, что его ответ реально продвинул проект.

### 7.6 Поведение на потоке

- запрос данных не роняет прогон — остальное считается и идёт дальше;
- если данные так и не пришли — требование остаётся «сделаем, как получим
  данные», и это честно отражается в итоге (а не выдаётся за готовое).

## 8. Архитектура (по слоям, SOLID)

### domain/ (чистые данные, без ввода-вывода)
- `Capability`, `Maturity` (надёжное/пробное), `CapabilityLimits`,
  `CapabilityBoundaries` — переименование и расширение `AgentCapabilitySpec`.
- `FeasibilityVerdict`, `CapabilityGap`, `DataRequest` — новые.

### application/ (оркестрация, по одной ответственности на сервис — SRP)
- `CapabilityMatcher` — сопоставляет требование с умением (тестируемо отдельно).
- `LimitChecker` — проверяет пределы (открыт для новых измерений — OCP).
- `FeasibilityAssessor` — собирает шаг: сопоставление + пределы + проход
  «почему не выйдет» + вердикт.
- `CapabilityGapRecorder` — записывает непокрытое как пробел (не выбрасывает).
- `DataRequestService` — создаёт/закрывает запросы данных; запускает
  переоценку зависящих требований.
- `CapabilityPromotionService` — пробел → пробное → надёжное, через механизм
  решений.
Все сервисы зависят от протоколов (LLM-провайдер, хранилище) — DIP; маленькие
интерфейсы — ISP.

### infrastructure/
- хранение вердиктов/пробелов/запросов данных (таблицы sqlite);
- загрузка вида `capability` из `templates/capabilities/*`.

### interfaces/
- API: список/закрытие запросов данных; список пробелов; повышение умения.
- UI: раздел «Нужно от вас», бейджи L1, сводка реализуемости.

### Принципы SOLID на практике
- **SRP:** сопоставление ≠ проверка пределов ≠ запись пробела ≠ повышение.
- **OCP:** новое умение — новый YAML, без правки кода; новое измерение предела —
  расширение `CapabilityLimits` + одна проверка.
- **DIP/LSP:** сервисы поверх протоколов, а не конкретных классов.

## 10. Что меняется относительно версии коллеги

Сохраняем: идею проверенного каталога с явными запретами, заземление оценки в
контрактах, разбиение Слоя 2, сильные тесты, честный `executor` через
специализацию промпта.

Добавляем/чиним:
- **пределы и границы** умения (ловят «слишком сложное/надёжное/большое»);
- **умолчание «не сделаем»** + защита от выдумывания (доказательство, проход
  «почему не выйдет», спорное — человеку);
- **пробелы в умениях** вместо молчаливого отказа + безопасный рост каталога;
- **запрос данных** как отдельный канал с понятным UX, а не повод для отказа;
- замыкание «не сделаем/условия» в существующие пробелы/уточнения/эскалации;
- честные имена (умение вместо агента; направление реализации — отдельно);
- версии в `covered_by`; адаптивный Слой 2 по активным умениям.
