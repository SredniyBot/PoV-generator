# Harness-агенты: исполнение выбранных задач автономными агентами

Статус: проект (design), к реализации после согласования.

Развилки, выбранные заказчиком:
- **Провайдеры** — несколько серьёзных внешних harness-систем на выбор, с
  курируемыми дефолтами (а не единственный встроенный исполнитель). Нужна
  чистая подключаемость.
- **Песочница** — Docker-контейнер.
- **Побочные эффекты** — только внутри песочницы; наружу отдаются артефакты,
  внешних действий (push/deploy) на первом этапе нет.
- **Порядок** — сначала дизайн-документ, затем поэтапная реализация.

## 1. Потребность / JTBD

Сейчас система **описывает** задачи: каждый лист-шаг через один вызов
`chat_json` производит структурный артефакт (спеку/отчёт/план). Нужно дать
системе возможность **исполнять** выбранные задачи автономными агентами
(harness) — многошаговыми, работающими в рабочем каталоге с инструментами
(правка файлов, shell, тесты) — и получать от них реальные артефакты (код,
наборы файлов, документы, данные) внутри того же управляемого цикла.

**JTBD:** «Когда у меня есть готовый контракт/спека задачи, я хочу поручить её
исполнение конкретному агенту на мой выбор и получить готовый артефакт внутри
общего цикла: с контекстом, валидацией, провенансом, бюджетом и откатом — не
выходя из системы и не теряя управляемости».

Это не отдельная подсистема сбоку, а **второй бэкенд исполнения за тем же
контрактом артефакта**.

## 2. Что уже есть в системе (швы, на которые опираемся)

- **Поле `executor` в шаблоне задачи** (`domain/registry.py`:
  `ExecutorType = Literal["llm","script","tool","human","hybrid","system"]`).
  Объявляется на каждом листе; сегодня реально все пути сводятся к `chat_json`,
  а «agent» — лишь пролог в промпте (`_render_capability_pledge`), не автономия.
- **Контракт артефакта как шов.** Лист = «произвести артефакт роли R по
  контракту C» (`produces.artifact`). Downstream (валидация →
  `ClarificationCoordinator` → патчи → planner → rollback) завязан на
  **артефакты, а не на способ их получения**.
- **Зеркальный слой провайдеров LLM** (`infrastructure/llm/`): `protocol.py`
  (`runtime_checkable` Protocol `chat_json`), `providers/*.py`, `registry.py`
  (резолв из шифрованных настроек: `purpose → assignment → routing →
  connection`, switch по `provider_type`). Готовый образец для harness-слоя.
- **Диспетчинг исполнения** — `execution_service.execute_task` (точка, где
  выбирается путь исполнения; сейчас branch по `active_provider`).
- **Асинхронный рантайм** — `WorkflowRunnerService` (демоны-потоки,
  `workflow_runs`), `CancellationToken` + форсированная отмена, per-workspace
  write-coordinator, `ParallelWorkflowScheduler`.
- **Настройки** — `SqliteSettingsStore` + `secret_box` (Fernet), маршрутизация
  «класс задачи → модель». Готовый образец для «класс задачи → harness».
- **Артефакты, провенанс, откат** — таблица `artifacts` (+ `created_by_task_id`,
  версии `parent_artifact_id`, иммутабельность EC4), `step_checkpoints` +
  механизм отката (`rolled_back_by`), `execution_runs`/`execution_traces`,
  учёт `llm_usage`.
- **Гейты качества** — kind `quality_gate`; контракты с `unstructured: true`.
- **Полупустой целевой шаг уже есть** — `implementation.component_build_spec`
  (fan-out по компонентам, `component_build_fanout`), в summary прямо назван
  «спека, которую можно отдать исполнителю (harness)». То есть конвейер уже
  готовит вход для harness; не хватает самого исполнителя.

Вывод: ~70% инфраструктуры уже есть. Работа — добавить **симметричный harness
и его рантайм**, не трогая downstream.

---

## 3. Ключевая идея: контракт артефакта — шов интеграции

Кто произвёл артефакт роли R — один LLM-вызов или автономный агент в песочнице
— деталь реализации за границей исполнения. Поэтому harness встраивается как
ещё один исполнитель, отдающий **тот же `ExecutionBundle`** (артефакты + usage +
trace), что и LLM-путь. Принципы: OCP (добавляем бэкенд, не меняя downstream),
SRP (рантайм песочницы отделён от движка задач), DI (провайдер резолвится из
настроек).

## 4. Доменная модель и контракты

### 4.1 Контракт исполнителя (новый Protocol)

`infrastructure/harness/protocol.py` — зеркало `llm/protocol.py`:

```
HarnessRunSpec:
  brief: str                      # рендер из ContextManifest + методология +
                                  # capability_pledge + контракт + критерии приёмки
  expected_artifacts: tuple[ExpectedArtifact, ...]
                                  # (role, contract_schema|None, формат: json|markdown|files)
  inputs: HarnessInputs           # входные артефакты (как файлы) + seed-репозиторий/каталог
  sandbox: SandboxHandle          # выделенная песочница (каталог внутри контейнера)
  limits: RunLimits               # wall_clock_s, max_tokens, max_steps, max_cost_usd
  model_hint: str | None          # модель для агента (если применимо)
  cancellation: CancellationToken | None

HarnessRunResult:
  status: completed|failed|cancelled|needs_input|partial
  artifacts: tuple[HarvestedArtifact, ...]   # role -> content(JSON/markdown) | bundle(path/hash)
  transcript: str                            # человекочитаемый ход работы (для L3/L4)
  tool_calls: tuple[ToolCall, ...]           # лог инструментов (best-effort)
  diff: str | None                           # git-дифф изменений в песочнице
  usage: LLMUsage | None                     # токены/стоимость (best-effort; None = n/a)
  clarifications: tuple[ClarificationCandidate, ...]  # блокеры -> через CE1
  error: str | None

HarnessProvider (Protocol):
  name: str
  def run(self, spec: HarnessRunSpec) -> HarnessRunResult: ...
  # опционально (стриминг): on_event callback / generator событий прогресса
  def capabilities(self) -> HarnessCapabilities: ...   # см. 5.3
```

### 4.2 Привязка к шаблону задачи

- Значение `executor: harness` (расширяем `ExecutorType`). Лист с
  `executor: harness` исполняется harness-слоем.
- Шаблон объявляет **критерии приёмки** (Definition-of-Done) машинно: какие
  артефакты обязаны появиться + какие гейты пройти (build/test/lint). У
  `component_build_spec` уже есть поле `acceptance` — делаем его машинным.
- `harness_eligible` (опционально): шаблон, который *может* идти и через LLM, и
  через harness — тогда выбор делает назначение/override (см. 5.4).

### 4.3 Brief (постановка для агента)

Методология (как думать) остаётся wrapper'ом; `ContextManifest` рендерится в
**brief** — самодостаточную постановку: цель, входные артефакты (как файлы в
песочнице), ожидаемые результаты и куда их положить, ограничения/`cannot_do`
(из `capability_profile`), критерии приёмки, бюджет. Рендер brief — отдельная
функция (тестируемая в изоляции), общая для всех адаптеров.

## 5. Слой провайдеров: подключаемость и выбор (центральная часть)

Заказчик: «встроенного минимального не хватит; нужны серьёзные, но не один —
дать выбор пользователю, с дефолтами; продумать как лучше». Решение —
нормализованный контракт + тонкие адаптеры + Docker-песочница + сбор
результата по соглашению + настройка выбора с курируемыми дефолтами.

### 5.1 Тонкие адаптеры поверх общего рантайма

Общая обвязка (провижн песочницы, посев входов, рендер brief, сбор результата
по соглашению, teardown) живёт в `HarnessExecutionService` + `SandboxRuntime`.
Адаптер каждого harness'а — **только** перевод нормализованного `HarnessRunSpec`
в конкретный вызов агента внутри контейнера и парс результата обратно. Так
адаптеры маленькие и однотипные, а различия систем не протекают в ядро.

### 5.2 Сбор результата (harvest) — две стратегии, выбирает контракт

1. **По соглашению (manifest):** brief требует от агента положить каждый
   ожидаемый артефакт в известный путь (`/work/.povgen/out/<role>.<ext>`) или
   записать `/work/.povgen/result.json`. Подходит для структурных артефактов.
2. **По диффу (bundle):** захватываем git-дифф/изменённые файлы песочницы как
   файловый артефакт. Подходит для кода/наборов файлов.

Адаптер поддерживает обе; контракт артефакта (`format`) определяет, какую
применять. Это снимает зависимость от того, «как именно» конкретный агент
оформляет вывод.

### 5.3 Матрица возможностей (HarnessCapabilities)

Каждый адаптер декларирует: поддерживаемые модели/провайдеры, интерактивность
(нужен ли pause/resume), Docker-native vs нужна обёртка, языки/домены, умеет ли
давать usage, умеет ли git-дифф. Используется для (а) подсказок выбора, (б)
будущей capability-aware маршрутизации (домен задачи → подходящий harness).

### 5.4 Реестр, дефолты и выбор

- `infrastructure/harness/registry.py` — зеркало `llm/registry.py`:
  `_PROVIDER_BUILDERS` + `provider_type → adapter`, резолв из
  `SqliteSettingsStore`. Креды/образы — через `secret_box`.
- **Подключения harness** в настройках (как LLM-connections): тип, образ Docker,
  путь/эндпоинт, креды (эфемерно), модель по умолчанию, лимиты.
- **Назначение «класс задачи → harness»** (зеркало «класс → модель»): для каждого
  класса/назначения — какой harness и с какой моделью. Поставляем **разумные
  дефолты** (несколько включённых из коробки, один — дефолтный).
- **Override на проект/задачу** в UI: «исполнить как агента» + выбор harness для
  конкретного шага (это и есть «выбирать конкретные задачи как агенты»).
- Если для класса нет назначения/harness не настроен — шаг падает явно
  (fail-loudly), либо (если `harness_eligible`) откатывается на LLM-путь —
  политика настраивается.

### 5.5 Кандидаты-адаптеры (первый набор)

- **Claude Code** (claude-agent-sdk / `claude` CLI headless) — у нас уже есть
  `claude_subscription`; зрелый агент с инструментами.
- **Aider** — git-aware CLI, много моделей (litellm), неинтерактивный режим
  (`--message --yes`), естественные git-коммиты (удобно для bundle/diff).
- **OpenHands** (OpenDevin) — контейнерный агент-рантайм; ложится на Docker-выбор.
- **Generic command-harness** — запуск произвольной команды в песочнице с
  шаблонным brief (escape hatch / интеграция нестандартного агента).
- **stub-harness** — детерминированные фикстуры (`templates/harness_fixtures/`)
  для тестов/CI; **не** пользовательский бэкенд, а тест-дубль.
- **Встроенный минимальный** (LLM + цикл инструментов) — опциональный
  no-Docker fallback, не headline; полезен там, где Docker недоступен.

Первый набор «из коробки» уточним на Ф1, но архитектурно их ≥2 и они
взаимозаменяемы за `HarnessProvider`.

## 6. Песочница (Docker)

`SandboxRuntime` (инфраструктура), абстрагирует движок среды (Docker сейчас;
позже — удалённый/локальный):

- **Жизненный цикл:** provision (поднять контейнер из образа адаптера) → seed
  (смонтировать/скопировать входные артефакты как файлы + seed-репозиторий,
  `git init` для diff-harvest) → run (запустить агента с лимитами,
  супервизия) → harvest (извлечь артефакты по 5.2) → teardown (снести контейнер;
  при ошибке — сохранить для диагностики по флагу).
- **Образы:** базовый образ на адаптер (с установленным агентом и тулчейном);
  версионируется; пользователь может указать свой образ в подключении.
- **Сеть:** по умолчанию запрет egress (sandbox-only, безопасность); разрешённые
  хосты — белый список в настройках (напр. для скачивания зависимостей).
- **Лимиты:** CPU/RAM/диск/время контейнера + лимиты прогона (токены/шаги/$).
- **Отмена:** `CancellationToken` → `docker stop`/kill контейнера; частичный
  результат сохраняем как `partial`.
- **Кросс-платформенность:** Docker — опциональная зависимость; при отсутствии
  Docker harness-провайдеры деградируют (как `mmdc` для Mermaid), а тесты идут
  на stub-harness. CI остаётся зелёным без Docker.

## 7. Хранение артефактов

- **Структурные** (JSON/markdown отчёты, спеки) → текущая таблица `artifacts`.
- **Файловые/бандлы** (дерево кода, дифф, набор файлов) → контент-адресуемое
  хранилище на диске под workspace (`artifacts/<artifact_id>/…`); в таблице —
  манифест + метаданные-указатель (роли, размер, хеши, тип бандла). Для версий и
  диффов уместен per-artifact git. **SQLite блобами не раздуваем.**
- **Иммутабельность/версии:** EC4 (исправление = новый артефакт),
  `parent_artifact_id` для цепочек версий.
- **Откат:** файловые артефакты архивируются флагом `rolled_back_by` (файлы на
  диске сохраняются) — полностью совместимо с механизмом отката.
- **Экспорт:** расширяем `export.zip` бандлами.

---

## 8. Валидация / Definition-of-Done

- Код проверяется **гейтами** (build/test/lint), а не JSON-схемой → контракт
  кода помечаем `unstructured: true`, проверку выносим в `quality_gate`
  (выполняется в той же песочнице после прогона).
- DoD машинный: «появились артефакты ролей R… и прошли гейты G…». Без явных
  критериев «готово» автономный агент непроверяем — поэтому acceptance в
  шаблоне обязателен для `executor: harness`.
- Неуспех гейтов → шаг `failed` с понятной причиной → штатный retry (модель
  попыток уже есть) или эскалация.

---

## 9. Безопасность и секреты

- **Изоляция:** контейнер, запрет egress по умолчанию, конфайнмент ФС
  (монтируем только песочницу), лимиты ресурсов. Произвольное исполнение кода —
  только в контейнере.
- **Секреты:** соблюдаем правило «система не хранит секреты». Креды агента/целевые
  токены подаются в песочницу **эфемерно** (env на время прогона, не персистим),
  фиксируем только факт «предоставлено» + несекретную заметку. Ключи
  harness-подключений — в `secret_box` (как LLM-ключи).
- **sandbox-only эффекты:** наружу — только артефакты; push/deploy/внешние вызовы
  выключены на первом этапе (зарезервированы под явный gate в будущем).

---

## 10. Рантайм и оркестрация

- **Раннер:** переиспользуем `WorkflowRunnerService` (async, `workflow_runs`).
  Harness-прогоны тяжелее LLM — отдельный **класс конкуррентности** (отдельный
  лимит параллельных контейнеров) поверх `ParallelWorkflowScheduler`.
- **Отмена:** `CancellationToken` → стоп контейнера; чекпоинт перед лист-шагом
  уже снимается (rollback-совместимость).
- **Стриминг прогресса:** транскрипт/вызовы инструментов → WS-проекция
  (live-лента активности агента в UI), как существующий `projection_changed`.
- **Бюджеты:** лимиты на прогон (токены/время/шаги/стоимость) + учёт в таблице
  рядом с `llm_usage`; оценка перед запуском. (Деньги/время — это governance-лимиты
  внутри системы, а не оценки, выдаваемые пользователю как гарантии.)
- **Человек в цикле (CE1):** прогон неинтерактивный; блокеры/неоднозначности
  агент возвращает как `ClarificationCandidate` → проходят штатным
  `ClarificationCoordinator`. Pause/resume mid-run — опционально позже.

---

## 11. Провенанс и аудит

Фиксируем на прогон: harness-провайдер+версия, образ песочницы, brief, seed,
транскрипт, лог инструментов, дифф, usage, произведённые артефакты. Расширяем
`execution_runs`/`execution_traces`; показываем в пирамиде L3/L4 (тем же
паттерном, что methodology-trace).

---

## 12. Детерминизм и тесты

- **stub-harness** + фикстуры (`templates/harness_fixtures/<role>.json|files`) —
  даёт канонические артефакты без запуска чего-либо; основной путь тестов/CI.
- `POV_HARNESS_DISABLED` — короткое замыкание (как `POV_MERMAID_DISABLED`).
- Тяжёлые провайдеры/Docker — опциональны, деградируют; CI кросс-платформенный
  (Linux/Win/macOS, py3.11/3.12) остаётся зелёным без Docker.
- Юнит-тесты: рендер brief, harvest-by-convention, dispatch в `execute_task`,
  резолв из настроек, маппинг результата в `ExecutionBundle`.

---

## 13. Совместимость с откатом

Harness-артефакты получают `created_by_task_id` → участвуют в графе зависимостей
и архивации отката без изменений. Чекпоинт pre-state снимается перед лист-шагом.
Важно: откат возвращает **состояние проекта и артефакты**, но не внешние
побочные эффекты — поэтому sandbox-only делает откат корректным по построению.

---

## 14. Полный цикл: спека → реализация

Конвейер уже даёт `component_build_spec` на каждый компонент (fan-out
`component_build_fanout`). Замыкаем цикл: отдельный objective/stage «исполнение
реализации», чьи лист-задачи — `executor: harness`, на вход берут
`component_build_spec` (+ контекст архитектуры), на выход дают артефакт-реализацию
компонента (bundle) и проходят гейты. Fan-out по компонентам уже существует —
harness исполняет каждую инстанцию.

---

## 15. UX выбора

- На завершённом/готовом шаге графа — действие «Исполнить как агента» + выбор
  harness (если несколько настроены).
- Live-лента прогона (транскрипт, вызовы инструментов, статус, бюджет).
- Просмотр файловых артефактов (дерево/дифф) + результаты гейтов.
- Настройки: подключения harness (тип/образ/креды/лимиты) + назначение
  «класс задачи → harness» с дефолтами.

---

## 16. Настройки

`SqliteSettingsStore` расширяем:
- `harness_connections` (тип, образ, эндпоинт, креды в `secret_box`, дефолт-модель,
  лимиты).
- `harness_assignments` (класс/назначение → harness + модель) с курируемыми
  дефолтами и сбросом-к-рекомендованному (как у LLM-assignments).

## 17. Фазы реализации

- **Ф0 — дизайн-документ** (этот файл) + согласование развилок.
- **Ф1 — контракт + реестр + настройки + stub.** `harness/protocol.py`,
  `harness/registry.py`, stub-harness + фикстуры, схемы настроек. Тесты на
  резолв/контракт. Без Docker.
- **Ф2 — движок + диспетчинг.** `HarnessExecutionService`, рендер brief,
  harvest-by-convention, маппинг в `ExecutionBundle`, dispatch
  `executor == harness` в `execute_task`. Сквозной тест на stub. Downstream не
  трогаем.
- **Ф3 — Docker-песочница.** `SandboxRuntime` (provision/seed/run/harvest/
  teardown, сеть-deny, лимиты, отмена). Образ под первый адаптер.
- **Ф4 — файловые артефакты + гейты.** Blob-хранилище + манифест в `artifacts`,
  `quality_gate` build/test/lint в песочнице, машинный DoD.
- **Ф5 — первые реальные адаптеры (≥2).** Например Claude Code + Aider за
  `HarnessProvider`; generic command-harness как escape hatch. Матрица
  возможностей.
- **Ф6 — рантайм-интеграция.** Класс конкуррентности, стриминг транскрипта (WS),
  бюджеты/учёт, отмена контейнера, провенанс L3/L4.
- **Ф7 — UI.** Выбор задач-агентов, выбор harness, live-лента, просмотр
  bundle-артефактов/гейтов, настройки подключений/назначений.
- **Ф8 — полный цикл + документация.** Objective/stage «исполнение реализации»
  на базе `component_build_spec`; раздел в `ARCHITECTURE.md`, статус этого
  документа.

Каждая фаза — отдельный коммит, с ruff + pytest + (для UI) build + рестарт, как
в предыдущих фичах.

## 18. Риски и анти-паттерны

- **Не** заводить harness как параллельный «другой execute_task» — это второй
  бэкенд за тем же контрактом артефакта (иначе дублирование downstream).
- **Не** хранить большие бандлы в SQLite — только на диске + указатель.
- **Не** давать агенту сеть/диск хоста по умолчанию (безопасность).
- **Не** хранить секреты — только эфемерная подача + факт «предоставлено».
- **Не** выпускать недетерминированный путь в тесты — stub-harness обязателен,
  Docker — опционален.
- Риск стоимости/времени harness-прогонов → жёсткие лимиты и оценка до запуска.
- Риск «агент сделал не то» → машинный DoD (гейты) + провенанс + откат.
