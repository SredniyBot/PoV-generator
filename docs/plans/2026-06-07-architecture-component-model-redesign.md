# Переработка архитектурного гейта: модель компонентов с контрактами

Статус: **реализовано** (Ф1-Ф6), в проде на ветке `integration/all-merges`.
Отталкивается от: прежней цели `architecture.system_design` (контекст →
компоненты → потоки → сборка `design_document`) и обсуждения с заказчиком
06-07.06.2026.

Что сделано по фазам:
- Ф1 — общий механизм диаграмм (`diagrams` на любом артефакте);
- Ф2 — `component_model` (контракты + внутренний состав + покрытие + реквизиты)
  и `deployment_map`; детерминированная проверка целостности вместо критика;
- Ф4 — живой поток архитектуры переведён на `component_model`/`deployment_map`;
  рендер `design_document` двухформенный (совместимость с закреплёнными графом);
- Ф5 — реквизиты (агрегация реализуемость+архитектура) + шлюз перехода на
  реализацию по блокирующим реквизитам; секреты не храним;
- Ф6 — слой реализации: веер по компонентам (`component_build_spec` на каждый
  компонент) + инъекция «своего» компонента в контекст (fanout_focus); сводка
  по умениям в `build_plan_synthesis`.

`component_decomposition` и ролевые `*_build_spec` оставлены в реестре (вне
активного графа) — для проектов с закреплённым старым графом.

---

## 1. Зачем это нужно (потребность)

Сейчас архитектурный гейт выдаёт **повествовательный документ**. Из-за этого:

- придумываются странные компоненты с размытыми зонами ответственности;
- компонентов слишком много — практически по компоненту на функцию;
- непонятно, как система работает на самом деле;
- потоки плохо читаются;
- описания компонентов, контрактов и развёртывания слабые;
- диаграммы есть только в фиксированных местах;
- **результат нельзя передать на реализацию** — нет структурированной,
  адресуемой, самодостаточной модели; нельзя проитерировать «по компоненту →
  harness-задача со всем контекстом».

Корень один: **архитектура производит прозу, а нужен структурированный,
самосогласованный каталог компонентов с контрактами**, где документ для человека —
это рендер модели, а не источник истины.

Цель: получить документ, который чётко определяет, какие компоненты будут, с
какими ответственностями, контрактами, внутренним составом и развёртыванием —
и при этом машинно пригоден как вход для последующей передачи компонентов на
реализацию.

---

## 2. Решения по итогам обсуждения (зафиксировано с заказчиком)

1. **Где живут детальные per-component документы для harness** — в **слое
   реализации**, не в архитектуре. Архитектура остаётся обзорной: модель +
   проверка + сборка. Контракт компонента — это шов между стадиями.
2. **Глубина контрактов** — средняя по умолчанию (операция + форма входа/выхода
   + ошибки + синхронность); глубже — только в критичных швах (деньги, внешняя
   граница интеграции, целостность данных, регуляторика).
3. **Гранулярность** — C4-lite (уровни). Количество компонентов и единиц
   развёртывания **минимизируем**; каждый сверх минимума — с обязательным
   обоснованием через драйвер. При этом соблюдаем стандарты разработки и чистую
   архитектуру.
4. **Шаг-критик** — **не делаем**. Заменяем на корректность по построению +
   детерминированную мягкую проверку (см. раздел 6).
5. **Ролевые спеки реализации** — убираем как отдельную генерацию. Ось
   генерации одна — по компоненту; по `capability` — только сводка-представление.
6. **На выходе — один документ на стадию.** Архитектура отдельно, реализация
   отдельно. Веер не плодит россыпь файлов для пользователя — он наполняет
   модель, сборка превращает её в один документ.
7. **Картинки — везде, где помогают понять**, через общий механизм диаграмм,
   а не фиксированные слоты. Правило: диаграмма там, где связи/поток/группировку
   проще увидеть, чем прочитать.
8. **Внутренний состав компонента — обязательный шаг** (верхнеуровневый: модули +
   их взаимозависимости). Минимизация снаружи компенсируется прозрачностью внутри.
9. **Реквизиты выявляем уже на этапе архитектуры** — per-component (данные для
   обучения, креды к API, файлы/таблицы, настройки, точный формат уже
   существующих у пользователя интерфейсов). Подсвечиваем на вкладке
   «Реквизиты», начинаем запрашивать, и **блокируем переход на реализацию** по
   непредоставленным блокирующим реквизитам. Секреты по-прежнему не храним —
   только факт «предоставлено».

## 3. Термины

| Термин | Что это |
|---|---|
| **Компонент** | логическая buildable-единица: одна ответственность, контракт на границе, внутренний состав. Адресуется стабильным id. Это единица передачи в реализацию. |
| **Модуль** | верхнеуровневая часть внутри компонента (для прозрачности «что внутри»). id — в пространстве имён компонента. |
| **Единица развёртывания** | физический рантайм-блок: что в каком процессе живёт. Компоненты отображаются на единицы развёртывания. По умолчанию одна. |
| **Контракт компонента** | предоставляемые и потребляемые интерфейсы + владение данными + события. Шов между архитектурой и реализацией. |
| **Слой** | архитектурный слой компонента (ядро / прикладной / адаптер / инфраструктура) — для проверки правила зависимостей чистой архитектуры. |
| **Драйвер** | причина разбиения (нефункциональное требование или принцип чистой архитектуры), которой обосновывается каждый компонент/единица сверх минимума. |
| **Карта покрытия** | соответствие «актор/внешняя система → обслуживающий компонент». Делает полноту обязательным заполнением, а не суждением. |

---

## 4. Раскладка по двум стадиям

**Архитектура** (`architecture.system_design`) — каталог и контракты, один
связный документ. Источник правды о составе системы.

**Реализация** (`implementation.build_plan`) — по документу-спеке на каждый
компонент для harness, сведённые в один документ; ось веера — компонент,
сводка — по `capability`.

Шов — **контракт компонента**: harness получает контракт самого компонента +
контракты соседей + системный контекст, а не весь документ.

## 5. Модель данных (артефакты архитектуры)

Порядок генерации топологический, без ссылок вперёд (важно для раздела 6):

```
system_context  →  component_model  →  interaction_view  →  deployment_map  →  design_synthesis
```

### 5.1 `architecture.system_context_definition` (уточняется)

Как сейчас, плюс: акторы и внешние системы получают **стабильные id** (короткий
ASCII), чтобы все нижестоящие шаги ссылались на закрытый набор.

### 5.2 `architecture.component_model` (НОВЫЙ — спина)

Заменяет `component_decomposition` и вбирает внутренний состав. **Одна генерация**
(компоненты + контракты + внутренние модули + покрытие видны модели в одном
ответе — внутренняя согласованность по построению). Класс `complex`.

```
components:                       # минимум; каждый сверх — с justification
  - id: ingest                    # стабильный короткий ASCII
    name: "Приём заявок"
    type: service                 # enum: service | datastore | queue | ui | scheduled | external
    layer: application            # enum: core | application | adapter | infrastructure
    responsibility: "..."         # ОДНА ответственность (проверяется, что одна)
    justification: "..."          # почему отдельный компонент (драйвер)
    capability_owner: capability.backend@1.0.0
    nfr: ["до ~100 заявок/мин", "..."]
    provided_interfaces:          # контракт «что предоставляю»
      - name: submitRequest
        sync: sync                # enum: sync | async
        criticality: normal       # enum: normal | critical
        input: "форма заявки {…}"
        output: "id заявки"
        errors: ["валидация", "дубликат"]
        # для critical — допускается углубление: schema, инварианты,
        # идемпотентность, гарантии порядка/доставки
    consumed_interfaces:          # контракт «что потребляю» — ссылки на id
      - component: store          # id другого компонента (закрытый набор)
        interface: saveRequest
    owned_data: ["черновики заявок"]
    events:
      emits: ["request.accepted"]
      consumes: []
    modules:                      # ОБЯЗАТЕЛЬНЫЙ верхнеуровневый внутренний состав
      - id: validator
        responsibility: "проверка формы"
        realizes: submitRequest   # какой предоставляемый интерфейс реализует
      - id: dispatcher
        responsibility: "постановка в очередь"
    internal_edges:               # зависимости модулей ВНУТРИ компонента
      - from: validator
        to: dispatcher
coverage:                         # полнота как обязательное заполнение
  actors:
    manager: [ingest]             # ключи = закрытый набор из system_context
  external_systems:
    crm: [store]
diagrams:                         # см. раздел 7 (общий механизм)
  - type: components              # диаграмма зависимостей
    caption: "Компоненты и связи"
    spec: { … }
  - type: internal               # по диаграмме на компонент
    caption: "Внутри: Приём заявок"
    of: ingest
    spec: { … }
```

Инварианты, которые становятся **обязательным заполнением** (а не проверкой
постфактум):
- `coverage.actors` / `coverage.external_systems` — ключи берутся из закрытого
  набора `system_context`, значение обязательно → «осиротевший актор» не
  выражается;
- каждый `provided_interface` закреплён за каким-то `module.realizes` →
  «висячий интерфейс без модуля» не выражается;
- `consumed_interfaces[].component` — выбор из закрытого набора id компонентов
  (в той же генерации) → ссылка не может «уехать».

### 5.3 `architecture.interaction_view` (уточняется)

Только **ключевые** сценарии (бюджет — потоки минимизируем, как и компоненты).
Получает закрытый список id компонентов/акторов и ссылается только на них.
Несёт `diagrams` (sequence/flow). Межартефактный шов (поток → компонент)
проверяется мягко (раздел 6).

### 5.4 `architecture.deployment_map` (НОВЫЙ)

Заменяет `common.deployment_topology` для архитектуры. Отображает компоненты на
единицы развёртывания. **По умолчанию одна единица** (модульный монолит); каждый
дополнительный split несёт `justification` с драйвером (независимое
масштабирование, другой рантайм, изоляция данных, разный темп изменений, разная
доступность). Несёт диаграмму развёртывания с границами единиц. Ссылается на
закрытый набор id компонентов.

```
deployment_units:
  - id: monolith
    name: "Основное приложение"
    runtime: "контейнер"
    components: [ingest, store]   # выбор из закрытого набора
    justification: "по умолчанию одна единица"
diagrams:
  - type: deployment
    caption: "Развёртывание"
    spec: { … }
```

### 5.5 `architecture.design_document` (остаётся ролью, синтез переработан)

`design_synthesis` собирает **один документ** = рендер модели: контекст,
компоненты с контрактами и внутренним составом, ключевые потоки, карта
развёртывания, риски (опц.), нефункциональные требования + **все диаграммы**.
Ничего не выдумывает — только связывает структурированные артефакты. Уверенность
финала не выше минимума по upstream (как сейчас).

### 5.6 Нефункциональные требования

Получают дом раньше декомпозиции (отдельный лёгкий шаг или поле в контексте) и
привязываются к компонентам (`components[].nfr`), чтобы разбиения были обоснованы
драйверами, а приёмка компонента — измерима. Точное место — на этапе реализации
фазы (см. раздел 10).

### 5.7 Реквизиты компонента (требуемые от пользователя входные данные)

Каждый компонент объявляет, что ему нужно **от пользователя**, чтобы его можно
было построить и запустить: данные для обучения, креды к API, файлы/таблицы,
настройки, точный формат уже существующих интерфейсов. Поле в `component_model`:

```
requisites:
  - id: ingest.crm_creds       # стабильный id (в пространстве имён компонента)
    kind: credential           # enum: credential | dataset | file | setting |
                               #       interface_format | sample | other
    title: "Доступ к API CRM"
    needed_for: "потребляемый интерфейс store.saveRequest"
    blocking: true             # блокирует переход на реализацию
```

Класс хранения выводится **из `kind` детерминированно в коде** (модель его не
выбирает — это защита правила «секреты не храним» по построению):

| `kind` | Класс хранения | Что храним |
|---|---|---|
| `credential` | sensitive | только факт «предоставлено» + нессекретная заметка (где лежит: env / vault). Значение — никогда. |
| `dataset`, `file` | reference | факт «предоставлено» + ссылка/расположение/владелец. Сами байты — не храним (приватность, объём). |
| `setting`, `interface_format`, `sample`, `other` | value | можно сохранить значение как контекст проекта (не секрет) — оно полезно как вход для harness (например, точный формат существующего API). |

Это значит: для `credential` в схеме нет поля под значение; персистер
отказывается сохранять значение для sensitive-классов. Тот же принцип
корректности по построению, что и в разделе 6.

## 6. Корректность по построению (вместо критика)

Приоритет: структура делает неправильный ответ трудно выразимым; проверка —
подтверждение и мягкая страховка, не ворота. Три линии защиты:

**Линия 1 — схема навязывает форму при генерации.** Вызов `chat_json(…, schema)`
(structured output) гарантирует форму. В схему вкладываем максимум: закрытые
перечисления (`type`, `layer`, `sync`, `criticality`), обязательные поля
(`responsibility`, `justification`, `capability_owner`), границы количества
(бюджет компонентов через min/max items). Целый класс ошибок невозможен.

**Линия 2 — порядок генерации и закрытый словарь ссылок.**
- топологический порядок без ссылок вперёд;
- ссылки — выбором из закрытого списка id, который кладётся в промпт явно
  («ссылайся только на эти»);
- взаимозависимое (компоненты + интерфейсы + внутренние модули + покрытие) — в
  **одной генерации** `component_model`;
- полнота — обязательное заполнение (карта покрытия, `module.realizes`), а не
  суждение постфактум.

**Линия 3 — минимизация уменьшает поверхность.** Меньше компонентов → меньше
рёбер и ссылок → меньше способов быть невалидным.

**Что остаётся проверке и почему это не тупик.** Узкая межартефактная проверка
ссылок (потоки → компоненты, карта развёртывания → компоненты) + правило
зависимостей чистой архитектуры (ядро не потребляет адаптер/инфраструктуру —
детерминируемо по `layer`). Проверка **неблокирующая** (как уже сделанный
механизм low-confidence / non-blocking валидации): нарушение → пишем конкретику
в зоны роста/допущения, снижаем уверенность, документ всё равно рендерится в
один файл с честной пометкой. Жёстко блокирует только схема — а её выполняет
сам провайдер. Опциональный точечный перезапрос с возвратом нарушения — держим
**выключенным по умолчанию**, вес несёт профилактика.

## 7. Общий механизм диаграмм

Сейчас диаграммы привязаны к фиксированным слотам в рендере
(`_build_flowchart`, `_build_interaction_diagram`, `_build_sequence`). Делаем
переиспользуемый блок `diagrams`, который умеет нести **любой** артефакт:

```
diagrams:
  - type: <context|components|internal|sequence|flow|deployment|data>
    caption: "..."
    of: <id компонента>      # только для type: internal
    spec: { … }              # структурный объект (узлы/рёбра или участники/сообщения)
```

- единый `_render_diagrams(diagrams)` диспетчеризует по `type` к существующим
  билдерам (переиспользуем `_build_flowchart` / `_build_interaction_diagram`);
- существующие фиксированные слоты рефакторятся на этот механизм
  (поведение-сохраняюще);
- генератор сам решает, где картинка помогает (правило из раздела 2.7); пустой
  `diagrams` — нормально, не декорируем ради декорации.

Это даёт диаграммы развёртывания, потоков данных, несколько потоков и
по-компонентные внутренние схемы в едином стиле (в PDF — через уже имеющийся
`mermaid_render`).

## 8. Шов к реализации (отдельная стадия, деталь — позже)

Слой реализации меняет ось веера с роли на **компонент**: берёт
`architecture.component_model`, на каждый компонент разворачивает harness-спеку
(контракт компонента + контракты соседей + системный контекст + `capability` +
критерии приёмки из nfr). Сводка — по `capability`. Итог стадии — один документ.
Стабильные id компонентов делают веер идемпотентным и совместимым с уже
сделанным закреплением графа. Полная проработка — отдельная фаза (раздел 9, Ф5).

## 9. Реквизиты: раннее выявление и шлюз перехода

Опираемся на уже существующий механизм, а не строим рядом:

- таблица `requisite_provisions(project_id, requisite_key, note, provided_at)` —
  хранит только факт «предоставлено» + заметку, **секреты не хранит**;
- `mark_requisite_provided` / `list_requisite_provisions`;
- проекция `project_requisites` → `ProjectRequisitesView` / `RequisiteItemView`;
- API `GET /requisites`, `POST /requisites/provide`; вкладка «Реквизиты» в UI.

### 9.1 Многоисточниковая агрегация

Сейчас `project_requisites` тянет из одного источника (последний
`feasibility_assessment`, поле `prerequisites`). Расширяем разбор
(`_extract_requisites`) до **нескольких источников**, объединяя в один список:

- реализуемость — `feasibility_assessment.capabilities[].prerequisites` (как сейчас);
- **архитектура — `component_model.components[].requisites`** (новое).

`RequisiteItemView` дополняется полями: `kind`, `blocking`, `stage`
(`architecture` | `realizability`), `source` (компонент / умение). Дедупликация —
по устойчивому ключу (`kind` + нормализованная цель), провенанс перечисляет все
источники. `requisite_key` для провижена делаем **устойчивым составным** (а не
сырым текстом), чтобы отметка «предоставлено» не слетала при переформулировке
заголовка ИИ.

### 9.2 Раннее выявление и запрос

Как только сгенерирован `component_model`, реквизиты появляются на вкладке
«Реквизиты» в статусе «нужно», сгруппированные по этапу/компоненту, блокирующие —
подсвечены. Плюс отдельный раздел «Реквизиты» в архитектурном документе — чтобы
человек видел их и при чтении, не только в UI.

### 9.3 Шлюз перехода на реализацию

Переход на `implementation.build_plan` блокируется, пока есть **непредоставленные
блокирующие** реквизиты. Реализация шлюза:

- проверка на сервере в `project_service.activate_next_objective` (отказ с понятным
  списком, что именно не предоставлено) — это «жёсткая» точка, минующая UI;
- в проекцию следующего objective (`workspace_query_service`) добавляем
  `blocked_by_requisites` (список) — UI гасит кнопку «следующий этап» с причиной.

Гранулярность блокировки — **per-requisite флаг `blocking`** (а не всё-или-ничего;
согласовано с заказчиком): блокируют только те реквизиты, без которых компонент
действительно не построить (креды к обязательному внешнему API, данные для
обучения). Остальные — видимы и запрашиваются, но не держат переход.

### 9.4 Подача вперёд

Реквизиты класса `value` (настройки, точный формат существующего интерфейса,
образцы), будучи предоставленными, становятся **контекстом для веера реализации**
(harness получает точный формат). `sensitive` и `reference` только шлюзуют и
информируют; их содержимое попадает в среду сборки вне нашего инструмента.

## 10. Фазы реализации

- **Ф1 — общий механизм диаграмм.** `diagrams`-блок + `_render_diagrams`;
  рефактор фиксированных слотов на него (поведение-сохраняюще). Быстрый выигрыш
  по читаемости, низкий риск. Тесты рендера.
- **Ф2 — `component_model` (спина).** Новый artifact_contract + task; структурная
  схема (контракты + внутренние модули + покрытие); закрытые словари в промпте;
  детерминированная неблокирующая проверка целостности + правило зависимостей.
  Stub-фикстура. Тесты.
- **Ф3 — `deployment_map` + уточнение `interaction_view`.** Новый artifact +
  task для развёртывания; потоки — бюджет + закрытый словарь id. Фикстуры, тесты.
- **Ф4 — переработка `design_synthesis`.** Сборка одного документа = рендер
  модели + все диаграммы; обновить `prepare_architecture_doc` (children) и
  `requires` синтеза. Обновить Python-схему `design_document`. Полный прогон.
- **Ф5 — реквизиты и шлюз перехода.** Многоисточниковая агрегация
  (`_extract_requisites` + источник `component_model`); поля `kind`/`blocking`/
  `stage`/`source` в `RequisiteItemView`; устойчивый `requisite_key`; класс
  хранения по `kind` (sensitive не персистит значение); `blocked_by_requisites`
  в проекции + шлюз в `activate_next_objective`; UI вкладки «Реквизиты»
  (группировка, блокирующие, гашение кнопки перехода). Тесты шлюза и хранения.
- **Ф6 — шов к реализации.** Веер по компонентам в слое реализации поверх
  `component_model`; сводка по `capability`; вывести из генерации ролевые спеки;
  подача `value`-реквизитов в контекст веера.
- **Ф7 — чистка и документация.** Депрекация старого пути
  `component_decomposition` (закрепление графа защищает прошлые проекты);
  ARCHITECTURE.md + спеки.

Каждая фаза: registry validate + pytest + ruff + (где трогаем UI) npm build +
перезапуск сервиса. Контракты не мутируем ретроактивно — новые артефакты вводим
новыми id/версиями, старые проекты держатся на закреплённом графе.

## 11. Риски и как их снимаем

| Риск | Снятие |
|---|---|
| «Не прошло валидацию» как тупик | Корректность по построению (раздел 6) + неблокирующая мягкая проверка; жёстко блокирует только схема, её выполняет провайдер. |
| Тяжёлая генерация `component_model` (всё в одном вызове) | Минимизация бюджета компонентов; класс `complex` (сильная модель). Запасной вариант — вынести внутренний состав в отдельный шаг с закрытым списком id (по умолчанию не делаем). |
| Поломка прошлых проектов сменой графа | Закрепление графа за проектом (уже есть) + новые id/версии артефактов. |
| Возврат «компонент на функцию» | Бюджет + обязательное `justification` через драйвер + правило «единица развёртывания по умолчанию одна». |
| Диаграммы-обои | Правило «картинка, где проще увидеть, чем прочитать»; пустой `diagrams` допустим. |
| Шлюз реквизитов как тупик | Блокируют только реквизиты с `blocking: true`; остальные не держат переход. Отказ перехода даёт понятный список «чего не хватает». |
| Утечка секрета в хранилище | Класс хранения выводится из `kind` в коде (не моделью); для `sensitive` в схеме нет поля под значение, персистер хранит только факт + нессекретную заметку. |
