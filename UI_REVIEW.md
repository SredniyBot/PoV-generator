## 1. Принципы для следующих волн редизайна

| # | Принцип | Что значит |
|---|---|---|
| **P1** | One primary status per screen | На L1 — одна главная активность; на L2 — одна категория объектов; на L3 — один объект. Сейчас многие экраны пытаются показать всё сразу. |
| **P2** | Бизнес-язык в primary surface, технический — за expert mode | Менеджер видит «уточнение», «согласование», «методология». Слова `template_ref`, `projection`, `blocking_scope`, `task_template` — за кнопкой «Технические детали». |
| **P3** | Visual hierarchy через цвет и размер, не layout | Сейчас все section-card'ы одинаково серые и одинаково крупные. Главное (например, открытое блокирующее уточнение) должно быть **визуально явно главнее** не из-за положения, а из-за tone. |
| **P4** | Drill-down без потери контекста | Карточка задачи / уточнения / артефакта — drawer/modal, не отдельная страница (где это уместно). Сейчас сделано непоследовательно. |
| **P5** | Адаптивность по «уровню вовлечённости» | Engagement level (`autopilot/balanced/control/expert`) сейчас управляет только частотой уточнений. Он должен влиять и на **что показывать**: в autopilot скрывать debug-вкладку, в expert разворачивать технические блоки. |

## 3. Что я бы делал в следующих 2-3 коммитах (моя рекомендация)

Высокая отдача, низкий риск:

1. **A1 + A2** (вкладки + удаление Activity) — это **структурная** правка, после неё всё остальное идёт чище.
2. **E1 + E3** (русские stage labels + читаемые provenance) — менеджер сразу почувствует ясность.
3. **C1 + C2** (technical hide + clarifications shortcut в header'е) — снимет когнитивный груз с шапки.

После них — F1 (форма создания), B1 (Hero-блок на L1), G2 (терминология).

Стопперы (нужно решение пользователя ДО старта):

- **A1**: согласовать ли финальный список вкладок (5 + dropdown — мой default; можно 4 без «Артефакты»; можно 6 с отдельной «Методология»)
- **F1**: какие именно пресеты проектов хотим (нужно от пользователя 3-5 примеров реальных запросов)
- **G1/G2**: словарь терминов — кто и где утверждает? Сейчас я могу сделать draft, но согласование лучше пройти с пользователем

## 4. Что НЕ делать (anti-roadmap)

- **Перепроектировать дизайн-систему с нуля.** Текущая палитра/токены работают. Если переделывать — то консолидировать в `tokens.css` отдельным шагом, не одновременно с features.
- **Менять навигацию URL.** Существующие маршруты `/projects/:id/overview|task-graph|...` уже завязаны на bookmarks/история. Только добавлять, не переименовывать.
- **Добавлять CSS-фреймворк (tailwind/mantine).** Текущий vanilla CSS читаем, добавление framework'а — большое touch без пропорциональной пользы.
- **Делать «один глобальный объект состояния» (Redux/Zustand).** React Query + useStoredState покрывают потребности. Добавление лишь усложнит.

## 5. Контракты, которые редизайн НЕ должен ломать

Эти инварианты UI закреплены в spec/10 и нарушать их нельзя:

- **UI1** — при открытии проекта пользователь попадает на L1, не на дерево задач.
- **UI2** — на L1 только важное и критичное.
- **UI3** — любой объект ведёт к источнику (задаче / событию / артефакту / правилу методологии).
- **UI5** — reasoning artifact задачи всегда виден как панель «Рассуждение» в L3.
- **UI6** — Provenance доступен с любого значимого поля артефакта одним переходом.

Все правки выше совместимы с этими инвариантами.
