# Семантика шаблонов задач

> **Статус:** v2.1 · черновик · 2026-05-09

Шаблон задачи описывает тип работы. Он не описывает глобальный сценарий выполнения, не выбирает порядок задач и не задаёт структуру рассуждения — последнее приходит из активного `methodology_pack` через wrapper во время выполнения.

---

## Композитная задача

Композитная задача:

- группирует область работы;
- раскрывается в `children`;
- объявляет `slots`;
- завершается по политике завершения;
- не исполняется как обычная листовая задача.

Пример:

```yaml
kind: task_template
id: common.analyze_solution
version: 1.0.0
title: Разобрать решение
type: composite

children:
  - id: outputs
    task: common.identify_solution_outputs@1.0.0

slots:
  - id: solution.evaluation
    title: Проверка качества решения
  - id: solution.explainability
    title: Объяснимость результата
```

---

## Листовая задача

Листовая задача:

- выполняет одно небольшое действие;
- имеет исполнителя;
- имеет обязательные и необязательные входы;
- производит один основной артефакт или результат взаимодействия;
- имеет путь валидации.

Листовая задача должна быть маленькой. Если в задаче есть несколько самостоятельных вопросов, ее нужно сделать композитной.

Пример:

```yaml
kind: task_template
id: ml.define_prediction_target
version: 1.0.0
title: Определить целевое событие прогноза
type: leaf
status: active

complexity: standard
executor: llm

requires:
  artifacts:
    required:
      - common.normalized_request@1.0.0

produces:
  artifact: ml.prediction_target@1.0.0   # только основной артефакт

context:
  include:
    - artifact.common.normalized_request

instruction: prompts/ml/define_prediction_target.md

# Опционально — только специфика задачи. Общая методологическая
# часть политики приходит из активного methodology_pack.
clarification_policy:
  may_generate_candidates: true
  ask_when:
    - missing_owner_decision
```

Шаблон не объявляет ни reasoning, ни methodology trace — они становятся
полями :attr:`ArtifactMetadata.reasoning` и :attr:`ArtifactMetadata.methodology_trace`
primary артефакта, формируются wrapper'ом активной методологии (см. ниже).

---

## Входы и допуск к запуску

`requires` задает минимальные входы для допуска:

- поля состояния;
- артефакты;
- активные доменные пакеты;
- решения;
- готовность.

Допуск проверяется без LLM. Необязательный вход может попасть в контекст, но не блокирует запуск.

---

## Контекст

`context` задает разрешенный состав `ContextManifest`.

Правила:

- исполнитель получает только манифест;
- контекст не может включать неразрешенные артефакты;
- политика переполнения контекста должна быть явной: `fail`, `trim_optional`, `summarize`, `decompose`;
- политика контекста не заменяет допуск к запуску.

---

## Slots

Slot — стабильная точка расширения композитной задачи.

Хороший slot:

```text
data.quality
spec.domain_sections
review.domain_gates
```

Плохой slot:

```text
before_step_3
after_analysis
```

Slot должен быть смысловым, а не позиционным.

---

## Reasoning через wrapper методологии

Шаблон задачи не описывает структуру рассуждения. Активный `methodology_pack` объявляет стадии (цель / JTBD / варианты / решение / ...), и runtime wrapper применяет их к каждому исполнению leaf-задачи.

Принципы:

- шаблон отвечает за специфику задачи: входы, основной артефакт, инструкцию исполнителя;
- methodology pack отвечает за форму рассуждения: какие стадии обязательны, какие правила проверяются, какие развилки эскалируются;
- эти оси ортогональны: смена методологии не требует правки шаблонов задач;
- на каждое исполнение порождается **один** primary артефакт (по `produces.artifact`); его `metadata.reasoning` соответствует схеме активной методологии, `metadata.methodology_trace` — трасса прохождения стадий и срабатывания правил (Этап 1.1 roadmap);
- режим `complexity` шаблона задачи влияет на то, какие стадии методологии применяются (через `complexity_overrides` в methodology pack).

Wrapper методологии не появляется в графе задач как отдельный узел. Это часть исполнения одной leaf-задачи.

## Merge как класс leaf-задач

> Этап 5 roadmap: merge — отдельная семантика leaf-задачи, объединяющей N входных артефактов в один результирующий.

Leaf-задача может объявить merge-блок:

```yaml
kind: task_template
id: common.requirements_spec_generation
type: leaf
executor: llm
merge:
  strategy: synthetic        # structural | synthetic | hybrid
  conflict_policy: union     # union | first_wins | last_wins | fail_on_conflict
requires:
  artifacts:
    required: [...]          # входы merge'а
produces:
  artifact: ...
```

### Стратегии

| Стратегия | Когда применять | Как исполняется |
|---|---|---|
| `structural` | Непересекающиеся домены, fan-out результаты, сводные индексы | Детерминированно через `application/merge_strategies.py`. **Без LLM.** |
| `synthetic` | Пересекающиеся артефакты, требующие связного нарратива (финальный ТЗ, обзорный документ) | Обычный LLM-путь (single_call или per_stage_cot). Промпт получает все входные артефакты как контекст. |
| `hybrid` | Скелет детерминирован + отдельные секции LLM-заполнены | Зарезервировано на будущее, в MVP не реализовано. |

### Conflict policy (только для `structural`)

Применяется когда два входа имеют одно и то же поле/элемент:

- `union` — для списков: объединение с дедупликацией. Для скаляров: `first_wins`.
- `first_wins` — берётся значение из первого входного артефакта.
- `last_wins` — берётся значение из последнего входного артефакта.
- `fail_on_conflict` — `ConflictError`, если входы несогласованы.

### Метаинформация

После исполнения merge-задачи в `ArtifactMetadata.merge_strategy` фиксируется выбранная стратегия (`structural` / `synthetic`). UI и provenance используют это для отметки «синтез N → 1» и понимания происхождения артефакта.

Все входные артефакты merge'а попадают в `ArtifactRelations.input_artifact_ids` — граф зависимостей (Этап 1.3) знает, какие источники участвовали в синтезе.

### Чего merge не делает

- Не вызывает уточнения у пользователя (это путь обычных leaf-задач).
- Не модифицирует слой A/B напрямую (`structural` создаёт только artifact; эффекты на `ProcessState` идут через обычный `effects:` блок).
- Не подменяет квалификацию methodology wrapper'а — merge применяется **после** standard reasoning, если применима активная методология.

## Завершение и эффекты

Завершение листовой задачи:

- исполнение успешно;
- артефакт создан;
- артефакт прошел валидацию;
- эффекты применены слоем управления процессом.

Завершение композитной задачи:

- обязательные дочерние задачи завершены или корректно пропущены;
- нет блокирующих дочерних задач в ошибке;
- обязательные артефакты поддерева доступны;
- обязательные проверки качества пройдены.

Effects:

```yaml
effects:
  readiness:
    - data_sources_identified
  gaps:
    may_open:
      - common.missing_data_source
    may_close:
      - common.unknown_data_sources
```

Эффекты — это разрешенные изменения слоёв `ProjectKnowledge`/`ProcessState`, а не прямое право исполнителя менять состояние проекта.

## Валидация

Шаблон задачи может задавать:

- строгость схемы основного артефакта;
- минимальную уверенность;
- политику для кандидатов уточнений (специфичных задаче);
- обязательные проверки качества;
- политику исправления.

`metadata.reasoning` primary артефакта валидируется отдельно — по схеме, собранной из активного `methodology_pack` (обязательные стадии присутствуют, типы полей соответствуют объявленным `produces`). Несоответствие — провал валидации задачи.

Вопрос к пользователю не создается напрямую из результата задачи. Листовая задача возвращает `clarification_candidates`, а координатор уточнений решает, что делать: принять допущение, отложить вопрос, спросить пользователя или создать эскалацию.

---

## Уточнения

Листовая задача может обнаружить недостающую информацию. Это нормальный результат, если задача добросовестно извлекла максимум из доступного контекста.

Правила:

- задача формирует кандидаты уточнений, а не UI-вопросы;
- кандидат должен содержать причину, влияние, уверенность и область блокировки;
- если можно продолжить с безопасным допущением, задача должна предложить это допущение;
- если вопрос содержит несколько самостоятельных решений, его нужно разделить на несколько кандидатов;
- если неопределенность возникла из-за слишком крупной задачи, шаблон нужно декомпозировать.

Правила активной методологии (`methodology_pack.stages[].rules`) тоже эмиттят `ClarificationCandidate` — с `source_type: methodology`. Координатор уточнений работает с ними одинаково с кандидатами от задач.

Пример:

```yaml
clarification_policy:
  may_generate_candidates: true
  ask_when:
    - owner_decision_required
    - low_confidence_high_impact
  assume_when:
    - high_confidence_low_impact
  default_blocking_scope: task
```

## Инварианты

| ID | Правило |
|---|---|
| TS1 | Шаблон имеет тип `composite` или `leaf`. |
| TS2 | Композитная задача объявляет `children` и/или `slots`. |
| TS3 | Листовая задача имеет исполнителя и выход. |
| TS4 | Листовая задача решает один локальный вопрос. |
| TS5 | Slot является публичным контрактом для доменных пакетов. |
| TS6 | Входы для допуска проверяются детерминированно. |
| TS7 | Эффекты применяются только после валидации. |
| TS8 | Задача не задает вопрос пользователю напрямую. |
| TS9 | Шаблон не объявляет структуру рассуждения — она задаётся активным `methodology_pack`. |
| TS10 | Каждое исполнение leaf-задачи производит ровно один primary артефакт; reasoning и methodology trace — поля его метаинформации. |
| TS11 | Merge-задача (`merge: strategy: structural`) объединяет входные артефакты детерминированно, без LLM-вызова; результат валидируется по контракту выходного артефакта. |
| TS12 | Merge-задача (`merge: strategy: synthetic`) проходит обычным LLM-путём; стратегия фиксируется в `ArtifactMetadata.merge_strategy` для provenance. |
| TS13 | Все входные артефакты merge-задачи попадают в `ArtifactRelations.input_artifact_ids` — граф зависимостей знает источники синтеза. |
