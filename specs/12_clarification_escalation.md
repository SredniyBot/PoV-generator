# Уточнения и эскалации

> **Статус:** v2.2 · черновик · 2026-05-09

Документ описывает, как система решает, когда можно продолжать с допущением, когда нужно спросить пользователя, а когда требуется эскалация проблемы.

---

## Назначение

Система не должна задавать пользователю все вопросы, которые смогла придумать LLM. Она должна отделять действительно важные уточнения от вопросов, на которые можно ответить добросовестным допущением.

Цель механизма:

- минимизировать лишнее вмешательство пользователя;
- не скрывать критичные неопределенности;
- формулировать вопросы от бизнес-потребности, а не от внутренней реализации;
- сохранять все допущения, ответы и последствия в истории проекта;
- блокировать только ту часть работы, которую нельзя продолжать корректно.

---

## Основные понятия

| Понятие | Смысл |
|---|---|
| `ClarificationCandidate` | Сырой кандидат на вопрос, найденный задачей, валидацией, планировщиком или доменным пакетом. |
| `ClarificationDecision` | Решение политики: спросить, принять допущение, отложить, отбросить или эскалировать проблему. |
| `ClarificationRequest` | Вопрос, который реально показывается пользователю. |
| `ClarificationAnswer` | Ответ пользователя или подтверждение предложенного варианта. |
| `ClarificationEffect` | Разрешенное изменение состояния проекта после ответа. |
| `EscalationTicket` | Инцидент, требующий внимания человека из-за ошибки, риска, конфликта или повторного провала. |

`ClarificationRequest` и `EscalationTicket` не одно и то же.

Уточнение — это нормальная часть сбора требований. Эскалация — это сигнал, что система не может безопасно продолжать обычный процесс.

---

## Общий поток

```text
Задача / валидация / планировщик / доменный пакет / методологический пакет
  -> ClarificationCandidate
  -> Координатор уточнений
  -> ClarificationDecision
  -> допущение | отложить | вопрос пользователю | EscalationTicket
  -> ответ пользователя или подтверждение допущения
  -> проверенные эффекты
  -> обновление слоя A (положение) или слоя B (процесс)
  -> перепланирование графа задач
```

Правила активного `methodology_pack` эмиттят кандидаты со `source_type: methodology_pack` — например, при сопоставимой уверенности вариантов в стадии `decision` или при невыполненных требованиях стадии `goal_framing`. Координатор обрабатывает их одинаково с кандидатами от задач.

Исполнитель задачи не задает вопрос пользователю напрямую. Он может только вернуть кандидаты на уточнение.

## Контракт кандидата

```python
class ClarificationCandidate(BaseModel):
    candidate_id: UUID
    project_id: UUID
    source_type: Literal["task", "validation", "planning", "domain_pack", "methodology_pack", "quality_gate"]
    source_id: str
    need: str
    question: str
    description: str
    rationale: str
    impact: str
    severity: Literal["low", "medium", "high", "critical"]
    confidence_without_user: float
    visibility: Literal["principal", "architectural", "technical"]
    decision_owner_role: Literal["business", "client", "methodologist", "architect", "data_owner", "security"]
    default_assumption: str | None
    recommended_answer: str | None
    answer_mode: Literal["single", "multiple", "free_text", "confirmation"]
    options: list[ClarificationOption]
    affected_task_ids: list[UUID]
    related_artifact_ids: list[UUID]
    blocking_scope: Literal["none", "task", "subtree", "objective"]
```

```python
class ClarificationOption(BaseModel):
    option_id: str
    label: str
    description: str
    effect_preview: str
    confidence: float | None
```

`question` — основной вопрос в одно емкое предложение. `description` — самостоятельное описание ситуации на 3-10 предложений: что известно, почему возник вопрос, какой контекст важен и что изменится после ответа. `need` описывает потребность, ради которой задается вопрос. `impact` объясняет, что изменится в проекте после ответа.

Кандидат может прийти без доменных вариантов ответа, но в пользовательский вопрос он не должен попадать в таком виде. Координатор уточнений обязан перед показом вопроса вызвать LLM-подготовку уточнения: сформировать самодостаточное `description`, осмысленные варианты ответа, уверенность по каждому варианту, `visibility` и `decision_owner_role`. Базовые варианты допустимы только как технический fallback для тестового режима или недоступности LLM, но не как нормальный рабочий путь.

## Контракт вопроса

```python
class ClarificationRequest(BaseModel):
    request_id: UUID
    project_id: UUID
    status: Literal["open", "answered", "assumed", "deferred", "cancelled"]
    priority: Literal["low", "medium", "high", "critical"]
    title: str
    question: str
    description: str
    reason: str
    impact: str
    answer_mode: Literal["single", "multiple", "free_text", "confirmation"]
    options: list[ClarificationOption]
    recommended_option_id: str | None
    visibility: Literal["principal", "architectural", "technical"]
    decision_owner_role: Literal["business", "client", "methodologist", "architect", "data_owner", "security"]
    default_assumption: str | None
    affected_task_ids: list[UUID]
    related_artifact_ids: list[UUID]
    blocking_scope: Literal["none", "task", "subtree", "objective"]
    created_from_candidate_ids: list[UUID]
    selected_option_ids: list[str]
    free_text: str | None
    resolution_summary: str | None
```

Вопрос должен быть самодостаточным: пользователь должен понимать, зачем его спрашивают и что произойдет после ответа, даже если он впервые открыл проект.

В текущей реализации ответ хранится внутри `ClarificationRequest`: выбранные варианты, свободный текст и человеко-читаемое резюме решения. Отдельная сущность `ClarificationAnswer` может появиться позже, если потребуется аудит нескольких итераций ответа.

## Режимы участия пользователя и visibility

> Этап 3 roadmap: engagement-режимы — **пороги автономного решения**, не право доступа. Право видеть и оспорить любое положение универсально и не зависит от режима.

Каждый кандидат уточнения имеет поле `visibility: VisibilityLevel`
(см. `05_problem_state.md`) — оно отражает **важность** вопроса для проекта:

- `principal` — бизнес-цель, главное ограничение, целевой пользователь, критическое согласование;
- `architectural` — выбор подхода, контур решения, способ интеграции, методологический выбор;
- `technical` — детали реализации, конкретные библиотеки, тонкости поведения.

Режим вовлечённости пользователя определяет, **какие уровни visibility выводятся пользователю проактивно**:

| Режим | Проактивно спрашиваются уровни | Что система решает автономно |
|---|---|---|
| `autopilot` | `principal` | architectural + technical |
| `balanced` | `principal`, `architectural` | technical |
| `control` | `principal`, `architectural` | technical (стрицее пороги уверенности на architectural) |
| `expert` | `principal`, `architectural`, `technical` | — (по сути не решает за пользователя) |

`balanced` и `control` имеют одинаковое **покрытие**; различаются порогами уверенности при автоматическом принятии в architectural-зоне.

Выбор режима — постоянная настройка проекта. В UI он должен находиться в шапке проекта, рядом с основными действиями, а не внутри списка вопросов. При выборе режима пользователь должен видеть короткое пояснение к каждому варианту, чтобы понимать, как часто система будет привлекать его к решениям.

### Связь visibility и `decision_owner_role`

`decision_owner_role` — **информационная ось** (UI-группировка, CE11 LLM-driver при подборе формулировки). На решение ask/assume/defer **не влияет**. Дефолт visibility по роли:

| Роль | Дефолтная visibility | Обоснование |
|---|---|---|
| `business`, `client`, `security` | `principal` | Бизнес-цели и регуляторные ограничения — всегда заметны менеджеру |
| `data_owner`, `methodologist` | `architectural` | Контур данных и методологические развилки — выбор подхода |
| `architect` | `technical` | Технологические детали реализации |

Эмиттер кандидата может переопределить дефолтную visibility явно (например, gate signoff с `decision_owner_role=client` имеет visibility=`principal` по дефолту — что согласовано с тем, что внешнее согласование всегда principal).

## Матрица решений координатора уточнений

Алгоритм `_decide_action(candidate, mode)`:

1. Если `candidate.visibility ∈ proactive_ask_levels(mode)` → `ask` (mode хочет surface этот уровень).
2. Иначе если есть `default_assumption` → `assume` (безопасный путь автономно принять допущение).
3. Иначе если `blocking_scope == 'objective'` → `ask` (страховка для gate-signoff'ов).
4. Иначе → `defer` (мягкий skip — менеджер видит в «Отложено»).

Confidence не участвует в решении ask/assume/defer; эмиттер сам решает, прикреплять ли `default_assumption` на основе своей уверенности.

Особые случаи, требующие явного эскалейта или блокирующего запроса:

| Ситуация | Действие |
|---|---|
| Есть юридический, ИБ или персональный риск | Эмиттер должен ставить `visibility=principal` (обычно `decision_owner_role=security`), что гарантирует surface на всех режимах. |
| Найден конфликт между источниками | Эмиттер ставит `blocking_scope` ≥ `subtree`; координатор всё равно отрабатывает по visibility. |
| Повторный провал валидации | Создать `EscalationTicket` или задачу исправления. |
| Нельзя продолжать без ответа | Эмиттер ставит `blocking_scope='objective'` — координатор `ask` даже вне proactive. |

## Когда спрашивать обязательно

Пользователя нужно привлекать, если вопрос:

- меняет цель проекта или критерии успеха;
- меняет границы работ, бюджет, сроки или ответственность;
- требует выбора владельца решения;
- касается персональных данных, ИБ, юридических ограничений или регуляторных обязательств;
- влияет на допустимость архитектурного или продуктового решения;
- блокирует создание обязательного артефакта;
- связан с конфликтующими вводными, которые нельзя разрешить из контекста.

---

## Когда не спрашивать

Вопрос не нужно показывать пользователю, если:

- ответ очевиден из контекста с высокой уверенностью;
- влияние на результат низкое;
- вопрос можно отложить без потери качества;
- можно явно зафиксировать безопасное допущение;
- задачу правильнее декомпозировать на более простые шаги;
- вопрос является технической деталью реализации, а не бизнес-решением.

---

## Формулировка вопроса

Правила:

- формулировать от потребности, а не от внутренней реализации;
- выносить основной вопрос в самый заметный заголовок;
- показывать ниже самодостаточное описание ситуации шрифтом меньшего размера;
- показывать достаточный контекст: что уже известно, почему вопрос возник и на какую часть проекта влияет ответ;
- объяснять причину вопроса и влияние ответа простым языком;
- всегда давать понятные варианты ответа с уверенностью системы по каждому варианту; варианты и уверенность формирует LLM на основе контекста проекта;
- использовать `answer_mode="multiple"`, если несколько вариантов могут быть выбраны одновременно;
- всегда оставлять возможность ответа в свободной форме, но не добавлять "другое" как отдельный вариант;
- не смешивать несколько независимых вопросов в одном;
- не использовать англо-русскую смесь без необходимости;
- не показывать пользователю сырой технический traceback как основной текст.

Плохой вопрос:

```text
Выберите feature store и метод drift detection.
```

Хороший вопрос:

```text
Как часто бизнес ожидает пересматривать качество прогноза после запуска?

Система готовит требования к аналитическому решению, которое после запуска должно оставаться проверяемым и управляемым. Сейчас в исходном запросе не указано, как часто бизнес ожидает оценивать качество прогноза и пересматривать выводы модели. Это влияет на требования к мониторингу, операционным отчетам, ролям ответственных сотрудников и критериям приемки. Если не зафиксировать это сейчас, ТЗ может либо переусложнить пилот, либо не описать важный контур сопровождения.
```

## Влияние на граф задач

Уточнение не обязано быть задачей в графе.

Правила:

- открытый блокирующий вопрос блокирует только указанный `blocking_scope`;
- неблокирующее допущение не мешает планировщику выбирать другие доступные задачи;
- ответ пользователя может разблокировать задачи, закрыть пробелы, создать новые задачи или включить доменный пакет;
- после ответа всегда запускается перепланирование;
- история вопроса отображается в ленте проекта.

---

## Влияние на состояние проекта

Ответ или допущение может создать только разрешенные изменения, разнесённые по двум слоям:

**Слой A — `ProjectKnowledge` (положения проекта):**

- добавить положение типа `fact` (новый подтверждённый факт);
- добавить положение типа `constraint` (новое ограничение);
- добавить положение типа `decision` (выбор между альтернативами);
- добавить положение типа `assumption` (рабочее допущение системы);
- отвергнуть положение через `RejectPositionPatch` при пере-открытии уточнения.

**Слой B — `ProcessState` (состояние процесса):**

- открыть или закрыть пробел;
- изменить готовность;
- активировать или отключить доменный пакет.

Эффекты применяются после валидации ответа и не должны напрямую мутировать состояние из UI.

Стабильный идентификатор положения, связанного с уточнением — `clarification.{request_id}`. Тип положения меняется по жизненному циклу (auto-assume → `assumption`; user answer → `decision`); идентификатор один, история переходов сохраняется в event log.

## UI и backend API

Уточнения отображаются как самостоятельная проекция проекта, а не как часть общего DTO проекта.

Backend endpoints:

- `GET /api/projects/{project_id}/clarifications` — список уточнений, счетчики открытых/отвеченных/принятых допущений и текущий режим участия.
- `GET /api/projects/{project_id}/clarifications/{clarification_id}` — детальная карточка одного уточнения.
- `POST /api/projects/{project_id}/commands/answer-clarification` — сохранить ответ пользователя.
- `POST /api/projects/{project_id}/commands/accept-assumption` — принять предложенное системой допущение.
- `POST /api/projects/{project_id}/commands/set-clarification-mode` — изменить режим участия пользователя.

После ответа или принятия допущения command layer запускает пересчет допустимых задач через планировщик. UI получает изменения через обычную realtime-модель проекций: `clarifications`, `situation`, `timeline`, `state`, `task_graph`, `debug`.

В интерфейсе уточнения должны быть видны в трех местах:

- в главном обзоре проекта — как центр вопросов, требующих участия пользователя;
- в истории событий — как понятные события "система запросила уточнение", "пользователь ответил", "принято допущение";
- в состоянии проекта — как зафиксированные допущения и решения, влияющие на дальнейшие шаги.

Правила отображения вопроса:

- если уточнение блокирует дальнейшую работу, оно должно попадать в главный фокус проекта, а не прятаться во вторичной панели;
- ответ на вопрос открывается в центральном модальном окне, потому что это временное решение пользователя, а не навигация в отдельный раздел;
- в модальном окне сначала показывается вопрос как главный заголовок, затем описание ситуации меньшим шрифтом, затем варианты ответа, затем свободное поле для комментария или собственного ответа;
- техническая метаинформация допустима только как вторичная информация и не должна визуально конкурировать с вопросом;
- варианты ответа обязательны для каждого вопроса; если доменный пакет не дал варианты, backend запрашивает их у LLM на основе контекста проекта;
- свободный ответ не считается вариантом и не должен отображаться как карточка "другое";
- поле собственного ответа визуально является такой же карточкой выбора, как остальные варианты, но содержит `input`;
- если пользователь последним сфокусировался на поле собственного ответа, выбранным считается именно собственный ответ, а ранее выбранные варианты сбрасываются;
- отдельная кнопка раскрытия "почему это важно" не нужна: существенный контекст должен быть сразу виден в описании вопроса.

## Интеграция с доменами

Доменный пакет может:

- добавлять доменные темы уточнений;
- задавать пороги обязательного вопроса;
- добавлять варианты ответа;
- связывать вопросы с доменными задачами, артефактами и проверками качества.

Доменный пакет не должен напрямую создавать вопрос пользователю при подключении. Он добавляет правила и задачи, а координатор уточнений решает, нужно ли спрашивать.

## Инварианты

| ID | Правило |
|---|---|
| CE1 | LLM не задает вопрос пользователю напрямую. |
| CE2 | Каждый вопрос имеет причину, влияние и область блокировки. |
| CE3 | Каждый ответ или допущение сохраняется в истории проекта. |
| CE4 | Обязательный вопрос нельзя молча заменить допущением. |
| CE5 | Неблокирующий вопрос не должен останавливать весь проект. |
| CE6 | Эскалация используется для исключительных ситуаций, а не для обычных уточнений. |
| CE7 | После ответа пользователя выполняется перепланирование. |
| CE8 | Основной вопрос визуально важнее описания, вариантов и технической метаинформации. |
| CE9 | Каждый вариант ответа имеет оценку уверенности системы или явно помечается как вариант без уверенности. |
| CE10 | "Другое" не является вариантом ответа, потому что свободный ответ доступен всегда. |
| CE11 | В рабочем режиме описание вопроса, варианты ответа, уверенность, `visibility` и `decision_owner_role` формирует LLM. |
| CE12 | Visibility — единственная ось решения ask/assume/defer; `decision_owner_role` — информационная ось без влияния на это решение. |
| CE13 | Право пользователя просмотреть, оспорить, переоткрыть, отвергнуть или повысить видимость положения универсально и не зависит от engagement-режима. |
| CE14 | Эмиттер обязан проставлять `visibility` явно либо позволить координатору вывести её из `decision_owner_role` через дефолт. |
