# Видение

> **Статус:** v2.1 · черновик · 2026-05-09

PoV Generator — это фреймворк для управляемого получения проектных артефактов из бизнес-запроса. Первый целевой сценарий — подготовка качественного технического задания, но модель должна расширяться на архитектуру, реализацию, тестирование, документацию и эксплуатацию.

---

## Цель

Система принимает:

- бизнес-запрос;
- документы и данные;
- уточнения пользователя;
- ограничения;
- решения и корректировки.

Система производит:

- структурированные артефакты;
- объяснимый ход работы;
- проверяемые промежуточные результаты;
- итоговый результат, прошедший контроль качества.

---

## Главная идея

Система не должна работать как один большой промпт и не должна идти по заранее заданному линейному маршруту.

Целевая модель:

```text
Цель
  -> Иерархический граф задач
  -> Композитные задачи со слотами
  -> Доменные расширения
  -> Листовые задачи
  -> Артефакты
  -> Уточнения и допущения
  -> Проверки качества
```

Сложная работа декомпозируется до маленьких листовых задач. Каждая листовая задача имеет понятные входы, контекст, исполнителя, выходной артефакт и проверку.

---

## Принципы

- **Потребность важнее генерации.** Система решает задачу клиента, а не просто пишет документ.
- **Глубокая декомпозиция.** Листовая задача должна быть маленькой и локально проверяемой.
- **Контроль LLM.** LLM работает внутри узкого контракта задачи.
- **Прозрачность.** Пользователь видит, что происходит, почему и на основании каких данных.
- **Воспроизводимость.** Манифесты контекста, трассы исполнения, артефакты и результаты валидации сохраняются.
- **Доменная расширяемость.** Новые домены добавляют расширения в слоты дерева задач.
- **Обоснованные уточнения.** Пользователь привлекается, только если без него нельзя добросовестно продолжать или нужно зафиксировать важное решение.

---

## MVP

Первый устойчивый сценарий:

```text
Бизнес-запрос
  -> дерево задач
  -> аналитические листовые задачи
  -> промежуточные артефакты
  -> ТЗ
  -> ревью
```

Для MVP важнее всего:

- корректная модель задач;
- понятная DSL-модель YAML;
- прозрачный планировщик;
- качественная работа доменных пакетов;
- ручная проверяемость в UI;
- retry и видимость ошибок.

Оптимизация токенов, промышленная многопользовательская эксплуатация и сложное развертывание не являются главным фокусом первого этапа.

---

## После MVP

Эти направления развития сознательно отложены за пределы MVP. Архитектура контрактов на них рассчитана: переход не должен ломать существующие задачи и доменные пакеты.

- **Per-stage CoT для методологии.** Вместо одного LLM-вызова на исполнение задачи — отдельный вызов на каждую стадию методологии с накопительным контекстом. Полезно для сложных доменов и более стабильного хода рассуждения. Контракт уже зарезервирован: `methodology_pack.stage_execution_mode = per_stage_cot`.
- **Несколько активных методологий на проект.** Например, разные методологии для аналитики и архитектуры. Поле `active_methodology_packs` уже массив; на MVP ограничено валидатором.
- **Динамический выбор сложности задачи.** Сейчас `complexity` статически объявлена в шаблоне. После MVP — pre-selector (haiku) перед запуском оценивает сложность по контексту и поднимает/опускает уровень.
- **Цепочка objective.** Передача артефактов между гейтами проекта (ТЗ → архитектура → реализация → ...) как явный механизм связи целей.
- **Стоимость как первоклассный сигнал.** Учёт токенов и стоимости в `ExecutionResult`, агрегированный счётчик на уровне `ProcessState`, бюджет проекта.
- **Тестовые фикстуры для шаблонов.** Каждый task pack содержит `examples/` с входами и ожидаемыми выходами для регрессии.
- **DAG стадий методологии** вместо линейной последовательности — для случаев условных переходов между стадиями.
