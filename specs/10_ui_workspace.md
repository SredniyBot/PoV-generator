# UI рабочего пространства проекта

> Статус: целевая спецификация v2.1 · 2026-05-09. Документ описывает пользовательское рабочее пространство и дизайн-правила. Технический контракт API и обновлений в реальном времени вынесен в `11_ui_realtime_api.md`.

## 1. Назначение

UI нужен не для демонстрации красивого пайплайна, а для управления живым процессом получения результата из исходного бизнес-запроса.

Принцип взаимодействия — **движение от общего к частному**. При открытии проекта пользователь видит только важное и критичное. Всё остальное доступно по требованию через drill-down.

С одного главного экрана пользователь должен понимать:

- какая цель сейчас решается;
- что система делает прямо сейчас;
- какие самые важные открытые вопросы и эскалации;
- какие ключевые артефакты уже получены;
- сколько проекту осталось до критериев завершения.

Технические детали, дерево задач, лента событий и трасса методологии — это уровни углубления, а не главный экран.

---

## 2. Иерархия экранов

```text
L1 — Project Overview          (mission control: что важно сейчас)
  └─ L2 — Списки и категории   (вопросы, артефакты, задачи, методология)
       └─ L3 — Карточка объекта (детали задачи / артефакта / уточнения / правила)
            └─ L4 — Provenance / trace (откуда что взялось)
```

Правила навигации:

- при открытии проекта пользователь попадает на L1, не на дерево задач;
- любой объект на L1 ведёт в L2 (свою категорию) или сразу в L3 (свою карточку);
- из L3 — drill-down в L4 для трассировки источника;
- ни один ключевой сценарий не требует уровней ниже L3 для базовой работы.

---

## 3. L1 — Project Overview

Главный экран. Единый источник ответа на вопрос «что сейчас важно».

### 3.1. Содержание

| Блок | Что показывает |
|---|---|
| Шапка | название и цель проекта, текущая стадия одной строкой («Сбор требований, ждём ответа клиента»), индикатор соединения, режим участия пользователя |
| Активность сейчас | что система делает прямо сейчас (выполняется задача, ждёт ответа клиента, ранжирует следующий шаг), последнее действие |
| Прогресс цели | визуально — какие обязательные артефакты `done_when` готовы, какие gates пройдены, что осталось |
| Критические вопросы | top-N открытых `ClarificationRequest` с `blocking_scope ≥ subtree` или `priority ≥ high` |
| Эскалации | активные `EscalationTicket` |
| Ключевые артефакты | последние одобренные artefacts + критичные в работе |
| Активная методология | один пак одной строкой со ссылкой на L2-карту методологии |

Пустые блоки скрываются. Если нет ни одной критичности — overview работает в режиме mission control: показывает прогресс, последние артефакты и текущее действие системы.

### 3.2. Правило попадания в overview

Объект показывается на L1, если выполнено хотя бы одно:

- `blocking` или эскалация;
- `severity` / `priority` ≥ `high`;
- требует пользовательского решения в текущем режиме участия;
- свежий ключевой артефакт (по белому списку контрактов проекта);
- активная задача (то, что сейчас выполняется или только что выбрано планировщиком).

Иначе объект уходит в L2-список своей категории.

### 3.3. Команды на L1

Минимальный набор всегда виден в шапке:

- запустить следующий доступный шаг;
- ответить на самое критичное уточнение;
- сменить режим участия пользователя;
- открыть карту методологии.

Команда показывается только если система может её выполнить. Если доступных задач нет — `run-next` возвращает предупреждение, не успех.

## 4. L2 — Списки и категории

L2 — это списки, в которые ведёт drill-down с overview.

| Список | Содержание |
|---|---|
| Уточнения | все `ClarificationRequest` (открытые, отвеченные, отложенные, принятые допущения) с фильтрами по статусу, приоритету, blocking_scope |
| Артефакты | все артефакты проекта с фильтрами по контракту, версии, статусу проверки |
| Задачи | дерево задач (TaskTree) — иерархия objective → composite → leaf с статусами и блокировками |
| Методология | карта активного `methodology_pack`: стадии, правила, политики уточнений, статистика применения |
| Лента | очищенная история событий проекта (`event_appended`) для аудита и навигации |

L2 не должен дублировать содержание L1 — это полные списки, а не краткие сводки.

---

## 5. L3 — Карточка объекта

L3 открывается из L1 или L2. Карточки разные для разных типов объектов.

### 5.1. Карточка задачи

- название и цель задачи;
- статус, исполнитель, сложность;
- активная методология, применённая к исполнению;
- входы и `ContextManifest`;
- выходы: основной артефакт, `reasoning_artifact`, `methodology_trace`;
- проверки качества и валидации;
- ошибки, возможность повтора.

Обязательная панель — **«Рассуждение»**: содержимое `reasoning_artifact` в человеко-читаемой форме (стадии методологии с их выходами):

- цель задачи (declared_goal);
- JTBD-фокус (если стадия активна);
- варианты с обоснованиями и уверенностью;
- выбранный вариант или эскалация со ссылкой на `ClarificationRequest`;
- кнопка «как это получилось» — переход в L4.

### 5.2. Карточка артефакта

- название, версия, контракт;
- задача-производитель;
- содержимое (с подходящим вьюером по формату);
- история валидаций и проверок качества;
- источники полей (через `_source` ссылки на правила методологии и входные артефакты);
- ссылки на reasoning_artifact того же исполнения.

### 5.3. Карточка уточнения

- основной вопрос крупным заголовком;
- описание ситуации (3–10 предложений) ниже шрифтом меньшего размера;
- варианты ответа с уверенностью системы по каждому;
- поле собственного ответа как такая же карточка с `input`;
- причина вопроса, влияние, область блокировки;
- источник кандидата (`source_type` + ref на конкретное правило/задачу);
- затронутые задачи и артефакты.

Открывается в центральном модальном окне (это временное решение, не навигация). Поведение модалки описано в `12_clarification_escalation.md` § 14.

### 5.4. Карточка правила методологии / стадии

- название стадии или правила;
- описание и рациональ;
- условие срабатывания;
- список применений в проекте со ссылками на конкретные задачи;
- статистика (сколько раз сработало, сколько эскаляций сгенерировало).

## 6. L4 — Provenance / trace

Уровень технической трассировки. Открывается по явному запросу пользователя («как это получилось»).

Содержимое:

- `methodology_trace` исполнения задачи: пройденные стадии, проверенные правила, сработавшие правила;
- `ContextManifest`: что попало в контекст исполнителя;
- LLM run и model parameters;
- цепочка `_source` от поля артефакта до правила методологии или входного артефакта;
- ссылки на родительские артефакты (по `parent_artifact_id`).

L4 не должен быть нужен для рутинной работы. Он нужен аудитору и при отладке.

## 7. Дизайн-система

Визуальное направление: строгая темно-серая рабочая среда с низким визуальным шумом.

Основные принципы:

- фон: графитовые и темно-серые оттенки, без агрессивных градиентов под текстом;
- поверхности: спокойные карточки с четкой иерархией;
- акцент: один основной цвет для активного действия, отдельные цвета для предупреждений и ошибок;
- типографика: хорошая читаемость русских текстов, умеренная плотность;
- анимации: только для важных событий, смены состояния, появления новых элементов;
- доступность: достаточный контраст, фокус-состояния, управление с клавиатуры.

Цветовые роли:

| Роль | Использование |
|---|---|
| Основной фон | вся рабочая область |
| Поверхность | панели, карточки, выпадающие списки |
| Поверхность выше | активные панели и открытые детали |
| Текст основной | заголовки и важное содержимое |
| Текст вторичный | пояснения и метаданные |
| Акцент | основное действие и выбранный объект |
| Успех | завершенные действия |
| Предупреждение | нет доступного шага, нужна проверка, возможна деградация |
| Ошибка | сбой выполнения, ошибка контракта, провал проверки |

## 8. Компоненты

| Компонент | Назначение | Уровень |
|---|---|---|
| `ProjectOverview` | главный экран mission control | L1 |
| `OverviewSection` | блок overview (активность, прогресс, критические вопросы и т.д.) | L1 |
| `ClarificationCenter` | список и карточка уточнений | L2/L3 |
| `ArtifactBrowser` | список и просмотр артефактов | L2/L3 |
| `TaskTree` | иерархия задач со статусами | L2 |
| `MethodologyView` | карта активного методологического пакета | L2 |
| `Timeline` | очищенная история событий | L2 |
| `TaskCard` | карточка задачи с панелью «Рассуждение» | L3 |
| `ReasoningPanel` | визуализация `reasoning_artifact` | L3 |
| `ProvenanceViewer` | трассировка источника | L4 |
| `CommandBar` | доступные команды | везде |

Все выпадающие списки, кнопки, поля ввода и уведомления используют единые стили дизайн-системы.

## 9. Команды пользователя

Команда должна быть доступна только если система может её обработать.

Минимальные команды:

- запустить следующий доступный шаг;
- повторить задачу в ошибке;
- ответить на уточнение;
- принять предложенное допущение;
- изменить режим участия пользователя;
- открыть артефакт или задачу;
- включить/отключить доменный пакет, если политика проекта это разрешает;
- сменить активный методологический пакет (требует прав методолога).

Если команда не может быть выполнена, UI объясняет причину до запуска или показывает предупреждение после попытки.

## 10. Уточнения пользователя

Уточнения — нормальная часть рабочего процесса, а не ошибка.

Правила отображения см. `12_clarification_escalation.md`. Здесь — UI-инварианты:

- критичный вопрос виден на L1 (overview);
- ответ на вопрос открывается в центральном модальном окне;
- описание вопроса самодостаточно — пользователь должен понимать ситуацию, даже если впервые открыл проект;
- варианты ответа обязательны и формируются LLM в координаторе уточнений;
- неблокирующее допущение не выглядит как авария.

Режимы участия:

| Режим | Как показывать |
|---|---|
| Автопилот | Только критичные и обязательные вопросы. |
| Сбалансированный | Блокирующие вопросы и вопросы с высоким влиянием. |
| Контроль | Дополнительно важные подтверждения. |
| Экспертный | Больше деталей, альтернатив и причин. |

Режим выбирается в шапке проекта на L1.

---

## 11. Адаптивность

На широком экране L1 показан целиком. L2/L3/L4 могут открываться в правой панели или новом полноэкранном виде по выбору пользователя.

На планшете часть L1-блоков становится вкладками или выдвижными панелями.

На мобильном экране:

- L1 — основной экран с переключателем разделов;
- L2/L3 — полноэкранные вьюшки;
- L4 — доступ через явное действие.

Ни один ключевой сценарий не должен требовать горизонтальной прокрутки.

## 12. Инварианты UI

| ID | Правило |
|---|---|
| UI1 | При открытии проекта пользователь попадает на L1, не на дерево задач. |
| UI2 | На L1 показано только важное и критичное; всё остальное — drill-down. |
| UI3 | Любой объект в UI ведёт к источнику: задаче, событию, артефакту, правилу методологии. |
| UI4 | Каждый пользовательский вопрос показывает причину, влияние и область блокировки. |
| UI5 | Reasoning artifact задачи всегда виден как панель «Рассуждение» в L3. |
| UI6 | Provenance доступен с любого значимого поля артефакта одним переходом до источника. |
| UI7 | Линейная нумерация не является основной моделью навигации. |
| UI8 | Ошибки, предупреждения и успешные события визуально различимы. |
| UI9 | Технические детали доступны на L4, но не засоряют L1–L3. |
