# UI/UX Design Brief

> Профессиональный редизайн интерфейса PoV Generator. Документ — не
> код. Он фиксирует **сценарии**, **информационную архитектуру**,
> **дизайн-систему** и **порядок реализации** до того как написана
> первая строка нового CSS.
>
> Это **черновик для согласования**. Каждый раздел заканчивается
> явной развилкой, на которую жду решение. Без подтверждения общего
> направления я не начинаю D1+ (реализацию).

---

## 0. Зачем нужен этот документ

Жалоба пользователя: «UX/UI выглядит костыльно. Сделать профессионально:
аналитик + архитектор + project manager + designer. Каждая кнопка на
своём месте, каждый шрифт обоснован, всё подкреплено бизнес-сценариями».

Сделать это **наугад** = высокий риск переделать на «ещё хуже» или
зря потратить день на правки, которые потом откатывают.

Профессиональный путь:
1. **Discovery** — кто пользователь, что он делает.
2. **Information architecture** — какие экраны, что где, почему.
3. **Design system** — токены и компоненты, чтобы УБРАТЬ инконсистентность.
4. **Page templates** — применить систему к каждому экрану.
5. **Implementation** — код.

Я уже сделал D0 (этот документ) и предлагаю порядок D1..D6. Жду
подтверждения общего направления перед реализацией.

## 1. Пользователи и роли

| Роль | Кто это | Engagement по умолчанию |
|---|---|---|
| **Менеджер проекта** | Бизнес-заказчик, инициирует проект, ждёт результата. Не разбирается в `task_template_ref`. | autopilot/balanced |
| **Постановщик / аналитик** | Может погрузиться в детали, отвечает на бизнес-вопросы, формулирует goal/scope. | balanced/control |
| **Методолог** | Меняет methodology pack, читает reasoning trace, оценивает качество вывода. | control/expert |
| **Архитектор / разработчик системы** | Расширяет реестр (domain packs, шаблоны задач, методологии). Использует CLI и провенанс. | expert |

**Главный пользователь UI = Менеджер**. Архитектор работает через CLI/код.
Аналитик и методолог — вторичные роли, доступ через «expert» переключатель.

> **Развилка 1.** Согласуй: главный = Менеджер. Если нет — изменю IA.

## 2. Бизнес-сценарии (user journeys)

### Сценарий M1. «Запустить проект и получить результат»

1. Менеджер заходит, видит список проектов и большую кнопку «Новый проект».
2. Открывает форму: название, **описание задачи в свободной форме**, степень вовлечённости (autopilot/balanced/control/expert).
3. Создаёт. Сразу попадает на **L1 Mission Control** проекта, где **одна главная вещь** — большая кнопка «Запустить» с пояснением.
4. Жмёт «Запустить». Видит **живой прогресс** (шаги выполняются один за другим).
5. По окончании — статус «Готово / Требует ответа / Заблокировано» + СRTA к нужному действию.

**Что сейчас не так**: после создания пользователь видит 7 вкладок и таблицы. Нет фокуса. Кнопка «Запустить» среди прочих в шапке.

### Сценарий M2. «Я на autopilot, что произошло?»

1. Менеджер ставит autopilot и нажимает «Запустить».
2. Workflow проходит до конца.
3. Менеджер хочет понять: **что система решила за меня?** Какие были вопросы, какие допущения приняла?
4. Открывает «Вопросы» → видит счётчик «🤖 Авто-решений: N» → переключает фильтр на «Допущения» → читает.

**Что сейчас не так**: счётчик добавлен в V1, но это **отдельная вкладка**. На L1 этого нет — менеджер должен сам догадаться зайти.

### Сценарий M3. «На меня прилетел блокирующий вопрос»

1. В шапке появляется badge «🔴 1 блокирующий».
2. Менеджер кликает → попадает в wizard на конкретный вопрос (не на список).
3. Видит **большой вопрос** в центре, **варианты ответа** карточками с указанной уверенностью.
4. Отвечает → wizard auto-advance к следующему открытому **если он есть**, иначе закрывается с тостом «Готово».

**Что сейчас не так**: wizard уже работает (W5.2), но на L1 нет вопроса напрямую — менеджер должен зайти на отдельную страницу.

### Сценарий M4. «Я хочу увидеть результат и поделиться»

1. Workflow закончен. Менеджер хочет посмотреть **итоговое ТЗ**.
2. На L1 видит «Готовые артефакты» — карточки с большим preview.
3. Открывает ТЗ → читает в reader-режиме.
4. Хочет — копирует markdown, экспортирует, перешлёт по почте.

**Что сейчас не так**: артефакты на отдельной вкладке, без preview на L1.

### Сценарий A1. «Аналитик хочет понять цепочку решений»

1. Открывает законченную задачу в графе.
2. Видит карточку «Рассуждение» (reasoning artifact).
3. Жмёт «Откуда это» → видит provenance (стадии методологии, правила, exec run, контекст).

**Что сейчас не так**: уже работает (W2.2 + W2.3). Только эстетика отличается от L1/L2.

### Сценарий E1. «Эксперт меняет методологию посередине»

1. На вкладке «Методология» видит активный пак.
2. Выбирает другой → подтверждение → методология сменена.
3. На L1 видит уведомление, что reasoning для будущих задач будет другой.

**Сейчас**: работает (W2.2), достаточно.

> **Развилка 2.** Согласуй сценарии: что важно, что лишнее, чего не хватает?

## 3. Информационная архитектура

### 3.1 Иерархия экранов (целевая)

```
ROOT
├─ /                            (список проектов)
├─ /new                         (создание проекта — отдельный flow)
└─ /projects/:id/
   ├─ overview                  L1 Mission Control      (главная)
   ├─ clarifications            L2 Inbox вопросов
   ├─ task-graph                L2 Граф задач (ReactFlow)
   ├─ artifacts                 L2 Артефакты
   ├─ timeline                  L2 Лента событий       (новое; вынести из Activity)
   ├─ methodology               L2 Карта методологии
   └─ settings                  L2 Настройки + Технические детали + Состояние
                                (объединить «Состояние» + «Замечания» + «Технические детали»)
```

**Текущие vs целевые вкладки**:

| Сейчас (9 вкладок) | Цель (5 + Settings) |
|---|---|
| Обзор | Обзор |
| Вопросы | Вопросы |
| Граф задач | Граф задач |
| Артефакты | Артефакты |
| Активность | Лента (узкий focus) |
| Методология | Методология (под Settings или отдельно — обсуждаем) |
| Состояние | (в Settings) |
| Замечания | (в Settings, либо встроен в карточку артефакта) |
| Технические детали | (в Settings / expert mode) |

Принцип: **5 основных вкладок + одна шестерёнка**. Не 9.

> **Развилка 3.** Согласуй финальный список вкладок. Альтернативы:
> - **A.** 5 вкладок + Settings (моё default)
> - **B.** 6 вкладок (отдельно Методология)
> - **C.** 4 вкладки (Обзор + Вопросы + Задачи (граф + лента) + Артефакты), всё остальное в Settings

### 3.2 Навигация и поведение

- **Sticky** topbar: бренд + проект + статус + counters (вопросы / прогресс / engagement).
- **Tabs**: горизонтальные, фиксированный шрифт. **Без иконок** — иконки на L2 cards/L3 drawer.
- **Breadcrumbs**: не нужны (max 3 уровня).
- **Sidebar**: только список проектов слева, сворачиваемый.
- **Drawer для L3**: задачи / артефакты / уточнения — открываются справа, не закрывают левый контекст полностью.

## 4. Дизайн-принципы

### P1. Одна главная вещь на экран
На L1 — крупный «Что сейчас». На L2-инбоксе — список со счётчиками. На L3-карточке — содержимое объекта. **Не пытаемся показать всё сразу.**

### P2. Прогрессия раскрытия
Менеджер сначала видит summary, потом по запросу — подробности.
- Карточка задачи: title + status. Кликнул → drawer с details. Кликнул в drawer «Provenance» → L4 modal.
- Это уже работает (W2). Поддерживаем во всех новых экранах.

### P3. Один первичный CTA на каждом контексте
- На L1 пусто: «Запустить» (большая, primary).
- На L1 в процессе: «Прервать» (secondary).
- На L1 с вопросом: «Ответить на N» (primary, заметная).
- На L1 с артефактом: «Открыть ТЗ» (primary).

### P4. Цвет — сигнал, не декор
- **Зелёный** только успех/завершено.
- **Жёлтый** только attention/warning.
- **Красный** только error/blocking.
- **Синий (accent)** — текущая активность, primary CTA.
- **Серые** — нейтральные элементы.

Каждый decorator меньше двух цветов на экран. Если на экране >2 цветных пятна — глаз не понимает приоритета.

### P5. Шрифты — три размера + два веса
- **24/32** display: только заголовок L1 hero.
- **18/24** title: section titles.
- **14/20** body: всё остальное.
- **12/16** meta: даты, технические refs.

Это **жёстко**. Не нужно «маленький-чуть-меньше-ещё-меньше».
Weights: 400 regular + 600 medium. Никакого bold для целых строк.

### P6. Spacing — кратно 4 (4 / 8 / 12 / 16 / 24 / 32)
Стандартный 8px scale. Между секциями — 32. Внутри карточки между блоками — 12 или 16.

### P7. Carded surfaces, мягкие границы
- Все content blocks — карточки на тёмной поверхности.
- Border radius `8px`, тонкая граница `1px rgba(255,255,255,0.06)`.
- Hover/focus — accent-цвет границы.
- Никаких тяжёлых теней.

### P8. Действие = первый персон
Buttons text: «Запустить», «Отменить», «Ответить», не «Run», «Cancel».

### P9. Технические термины — за expert mode
В autopilot/balanced/control видны бизнес-имена: «вопрос», «методология», «согласование заказчика».
Слова `task_template_ref`, `clarification_candidate`, `blocking_scope=objective`, `decision_owner_role` — только при `expert`, и помечены как «техническое».

> **Развилка 4.** Все 9 принципов — OK? Какой убрать, что добавить?

## 5. Design system (tokens)

Конкретные значения, которые лягут в `tokens.css`.

### 5.1 Type scale

```css
--font-family-sans: "Inter", "Segoe UI", system-ui, sans-serif;
--font-family-mono: "JetBrains Mono", "Cascadia Mono", ui-monospace, monospace;

--font-size-display: 24px;   /* L1 hero / project name */
--font-size-title: 18px;     /* SectionCard.title */
--font-size-body: 14px;      /* everything default */
--font-size-meta: 12px;      /* timestamps, IDs, small badges */
--font-size-mono: 13px;      /* code snippets */

--font-weight-regular: 400;
--font-weight-medium: 600;

--line-height-tight: 1.2;    /* display */
--line-height-snug: 1.4;     /* titles */
--line-height-normal: 1.5;   /* body */
```

### 5.2 Spacing

```css
--space-1: 4px;
--space-2: 8px;
--space-3: 12px;
--space-4: 16px;
--space-5: 24px;
--space-6: 32px;
--space-7: 48px;
```

### 5.3 Color palette

Намеренно скромный набор — 5 семантических + 3 surface.

```css
/* surfaces */
--surface-base: #0e1217;            /* page background */
--surface-elevated: #161b22;        /* card */
--surface-elevated-hover: #1c222b;  /* card hover */

/* text */
--text-primary: #e8ecf3;

/* lines */
--border-subtle: rgba(255, 255, 255, 0.06);
--border-strong: rgba(255, 255, 255, 0.16);

/* semantic */
--accent: #78b8c9;                  /* primary CTA, active state */

--warning: #d6ad59;                 /* attention, deferred */
--danger: #d78383;                  /* error, blocking, failed */
--info: #a884c6;                    /* secondary tags, hints */

/* per-role chip backgrounds (decision_owner_role) */
--role-business: rgba(120, 184, 201, 0.18);
--role-client: rgba(168, 132, 198, 0.18);
--role-methodologist: rgba(214, 173, 89, 0.16);

--role-data: rgba(180, 165, 134, 0.18);
--role-security: rgba(215, 131, 131, 0.18);
```

### 5.4 Radius / elevation

```css
--radius-sm: 4px;     /* chip, inline tag */
--radius-md: 8px;     /* card, button */
--radius-lg: 12px;    /* hero card */

--shadow-soft: 0 1px 0 rgba(255, 255, 255, 0.02), 0 2px 8px rgba(0, 0, 0, 0.3);
--shadow-elevated: 0 4px 16px rgba(0, 0, 0, 0.5);
```

### 5.5 Motion

```css
--motion-fast: 120ms;     /* hover, focus */
--motion-medium: 220ms;   /* drawer, modal */
--motion-slow: 420ms;     /* page transitions if any */
--motion-easing: cubic-bezier(0.2, 0.0, 0.0, 1.0);
```

### 5.6 Layout grid

- **Max content width**: 1280px (центрируется на десктопе).
- **Gutter**: 32px по бокам на ≥1024px, 16px на mobile.
- **Sidebar**: 280px when expanded; 56px when collapsed.
- **L1 hero**: full content width.
- **L2 lists**: full content width, items have max-width 800px для читаемости.
- **L3 drawer**: 480px wide right side.

## 6. Component conventions

Не пишу полный component library — это много. Закладываю **conventions** для уже существующих компонентов:

| Компонент | Текущее | Цель |
|---|---|---|
| `Button` (primary) | разнородный | один стиль: accent-bg, white text, 14px medium, 12×16px padding, radius-md |
| `Button` (secondary) | разнородный | transparent bg, border-subtle, text-primary, hover→accent-border |
| `StatusPill` | работает | сохранить, 12px meta, 4-цветовая семантика |
| `SectionCard` | работает | сохранить, добавить `tone` prop совместимый с palette выше |
| `Modal` | работает, но широкий | max-width 720px, padding 24, sticky footer на длинных формах |
| `Drawer` | работает | 480px right, slide-in 220ms |
| `LoadingPanel` | работает | заменить на skeleton screens где можно |
| Header counters | новое (V1) | стандартный chip-button pattern |

**Не делать**: ещё одну UI-библиотеку, ещё одну дизайн-систему. Просто **дисциплинированно** применять токены.

## 10. Анти-паттерны (NOT-TO-DO)

Из существующего UI, что точно надо переделать:

- **«Активность» вкладка** — kitchen sink (situation + timeline + tasks + clarifications + artifacts), визуально каждый блок одинаково тяжёлый. Разнести.
- **`povgen.provider` / `povgen.model` dropdown в шапке у менеджера** — это технический выбор. Перенести в Settings / expert mode.
- **`template_ref` и `task_key` в видимых местах** — заменить на читаемые имена шагов; ref-ы оставить в expert mode.
- **«Технические детали» как вкладка** — большая JSON-свалка. Превратить в expandable секцию внутри Settings.
- **9 вкладок** — слишком много, дробит внимание.
- **Mode dropdown в шапке** с длинным описанием — компактнее, через popover.

## Итог

Это **rebuttable defaults**. Я подождать твою реакцию по развилкам перед D1+ (реализация). Альтернативно: скажи «всё OK, поехали» — приступаю по плану D1..D11.

Существующие пользовательские потоки и URL-ы переживут редизайн. Backend контракт не задет (кроме мелких UI-views).
