## 1. Цель документа и метод

Профессиональный редизайн = **последовательность всё более конкретных
решений** от типа системы до пикселя. Пропустить уровень = построить
кривое здание (вкладки красивые, mental model сломана → продукт не
работает).

### 8 уровней проектирования

```text
Уровень 0  Тип системы и доминирующие UX-проблемы (challenges)
Уровень 1  Контекст пользователя (среда, частота, эмоции, окружение)
Уровень 2  Jobs to be done (functional + emotional + social + negative)
Уровень 3  Design challenges как открытые tensions
Уровень 4  Mental model & paradigm (push/pull, sync/async, doc/process)
Уровень 5  Information architecture
Уровень 6  Interaction patterns
Уровень 7  Visual design system (tokens, components)
Уровень 8  Prototype & test
```

В первой итерации я пропустил уровни 0–4 и сразу занялся 5–7. Это
привело к фиксации **преждевременных решений** (5 вкладок, hero CTA,
reader-режим, engagement slider). Документ пересобирается
последовательно. Старые секции остаются как след — не удаляются.

## 2. Уровень 0 — Тип системы

PoV Generator — это **delegated cognitive work с async checkpoints**:

- пользователь делегирует когнитивную задачу системе;
- система выполняет работу автономно с возвратами «решите вот это»;
- результат — артефакт, рождённый в сотрудничестве человека и системы;
- **доверие** — ключевой драйвер пользовательского опыта.

Категории-аналоги: AI coding agents (Devin, Cursor agent), AI legal
review, AI strategy advisors. **Не** CRUD, **не** дашборд, **не**
creative tool, **не** SaaS-классика. Это другой жанр UX.

### Доминирующие UX-проблемы (design challenges)

Эти tensions нужно разрешить хорошо, иначе любая красота UI ничего
не даст. Каждое решение IA / paradigm / экрана должно отвечать на
«улучшает ли оно один из C1..C7».

| # | Challenge | Напряжение | Хорошее решение |
|---|---|---|---|
| **C1** | Trust calibration | Доверять/нет — решение постоянное, не одноразовое | В каждый момент пользователь интуитивно понимает «здесь система уверена / здесь сомневается» |
| **C2** | Delegation gradient | Хочется делегировать, но страшно потерять контроль | Плавное «отпускание» от control → autopilot по мере опыта пользователя и его сигналов |
| **C3** | Context preservation | После 3 дней паузы пользователь забыл состояние проекта | Возврат восстанавливает контекст без чтения 50 экранов; «где остановились» очевидно |
| **C4** | Failure surfacing | LLM ошибается специфично (галлюцинации, пропуски, расплывчатый язык) | UI помогает заметить **именно эти классы** ошибок, не CRUD-баги |
| **C5** | Mental model alignment | Если пользователь думает «это база» — он не поймёт почему результат разный | Терминология / метафоры формируют правильную модель «фабрика производит артефакт по методологии» |
| **C6** | Handoff externally | Артефакт нужен в Confluence / PDF / презентации, не в нашей системе | Артефакт — first-class экспортируемый объект, передача — заложенный сценарий |
| **C7** | Recoverable mistakes | Ответил на вопрос → через день обнаружил «не так» | История решений + переоткрытие + понимание последствий повторного применения |

## 4. ⚠ HYPOTHESIS v1 — Пользователи

> Заметка: ниже — гипотезы первой итерации. Список ролей валиден как
> отправная точка, но **контекст работы каждой** (частота, среда,
> социальное окружение, эмоциональный фон) пока не подтверждён
> (открыто на уровне 1, см. §11).

Четыре роли. **Главный пользователь UI — Менеджер.** Остальные —
вторичные, доступ через `expert` переключатель или CLI.

### 2.1 Менеджер проекта (P0 — основной)

| Атрибут | Значение |
|---|---|
| Кто | Бизнес-заказчик проекта, постановщик, владелец результата |
| Контекст работы | Имеет бизнес-запрос, нужен артефакт (ТЗ для команды разработки) |
| Технический фон | Низкий. Не знает что такое `task_template_ref`, `manifest_id`, `decision_owner_role` |
| Частота | Несколько раз в неделю на проект; один проект может жить 1–5 дней активно, потом «приёмка» |
| Время на сессию | 10–30 минут. Прерывается на встречи. |
| Engagement по умолчанию | `autopilot` / `balanced` |
| Главная боль вне системы | «Писать ТЗ руками — неделя; передать аналитику — не уверен в качестве» |
| Главный страх в системе | «Я нажал autopilot, система что-то нарешала, я отдал ТЗ, а оно невпопад» |

### 2.2 Аналитик / постановщик (P1 — вторичный)

| Атрибут | Значение |
|---|---|
| Кто | Бизнес-аналитик в команде, может быть тот же менеджер «в режиме копать» |
| Контекст | Менеджер запустил проект; аналитик включается на этапе вопросов или когда менеджер не уверен в выводе |
| Технический фон | Средний. Понимает «требования», «scope», «допущения», но не код |
| Частота | По вызову; 2–5 раз за проект |
| Время на сессию | 30–90 минут глубокого вкладывания |
| Engagement | `balanced` / `control` |
| JTBD-фокус | Понять цепочку решений, ответить на вопросы среднего приоритета, проверить и поправить |

### 2.3 Методолог (P2 — экспертный)

| Атрибут | Значение |
|---|---|
| Кто | Архитектор процесса / методологии в организации |
| Контекст | Подключается, когда: а) меняется методология; б) идёт ретро по проектам; в) отлаживается новый domain pack |
| Технический фон | Высокий по доменной части, средний по системе |
| Частота | 1–2 раза в месяц на проект |
| Engagement | `control` / `expert` |
| JTBD-фокус | Видеть выполнение методологии по стадиям, какие правила сработали, какие — нет |

### 2.4 Архитектор системы (P3 — power user)

| Атрибут | Значение |
|---|---|
| Кто | Разработчик/архитектор, расширяющий реестр packs и шаблонов |
| Контекст | Работает с YAML, тестовыми фикстурами, CLI |
| Частота | Эпизодически, при внесении нового объекта в реестр |
| Engagement | `expert` (или вообще без UI) |
| JTBD-фокус | Через CLI / код. UI — только debug и provenance. |

> **Решение:** редизайн оптимизируем под P0 (Менеджер). P1/P2 получают
> те же экраны, но с раскрытым `expert`-слоем. P3 не оптимизируется
> в UI вообще — его рабочий контур это CLI и redaktor YAML.

## 5. ⚠ HYPOTHESIS v1 — JTBD-карта (нуждается в перепиcи)

> **Заметка:** большинство jobs ниже — это **способы работы в UI**
> («пройтись по вопросам пачкой», «увидеть допущения»), а не настоящие
> прогрессы в жизни пользователя. Переписать после уровня 1 в строгом
> фрейме: situation → motivation (без решения) → outcome (измеримый,
> переживает замену системы). См. обсуждение в чате от 2026-05-11.
>
> Пометки внутри секции отмечают где конкретно случился прыжок
> в solution-thinking.

Каждая работа = «когда [ситуация], я хочу [мотивация], чтобы [исход]».
Job, а не feature.

### 3.1 Менеджер (M-jobs)

**M-J1. Запустить проект и получить артефакт.**
> Когда у меня есть бизнес-запрос на новую функциональность / новый
> продукт, я хочу за минимальное время получить структурированное ТЗ,
> чтобы отдать его команде разработки и не тратить неделю на ручное
> написание.

Триггер: новый запрос от заказчика.
Исход успеха: на руках готовый артефакт (markdown / экспорт) + ощущение, что он годный.

**M-J2. Понять, что произошло на автопилоте.**
> Когда система отработала на autopilot без меня, я хочу увидеть **какие
> допущения она приняла за меня**, чтобы убедиться, что они разумные
> (или поправить).

Триггер: workflow закончен; я возвращаюсь к проекту.
Исход успеха: вижу список авто-решений с пометкой «применено по умолчанию», могу зайти, прочитать обоснование, при необходимости — отменить и переспросить.

**M-J3. Быстро ответить на блокирующий вопрос.**
> Когда система упёрлась в вопрос, который без меня не решить, я хочу
> увидеть его быстро, прочитать понятным языком, ответить и продолжить —
> чтобы не было простоя.

Триггер: уведомление / захожу в проект, вижу красный счётчик.
Исход успеха: за 2 минуты ответил, workflow поехал дальше.

**M-J4. Понять, где сейчас проект (без drill-down).**
> Когда я открываю проект через час/день, я хочу за 5 секунд понять:
> идёт работа / ждёт меня / готово, чтобы решить — отвлекаться сейчас
> или нет.

Триггер: открываю проект.
Исход успеха: смотрю на L1, через 5 секунд знаю состояние и primary CTA.

**M-J5. Получить результат и передать.**
> Когда проект завершён, я хочу увидеть итоговое ТЗ, скопировать или
> экспортировать его, чтобы отдать команде / отправить заказчику.

Триггер: workflow завершён.
Исход успеха: открыл артефакт в reader-режиме, скопировал markdown или сохранил файл.

**M-J6. Сравнить с тем, что я ожидал.**
> Когда я получил готовое ТЗ, я хочу понять — что система НЕ покрыла,
> где были компромиссы, какие признаны риски — чтобы пройтись и решить
> добавлять ли.

Триггер: получил результат.
Исход успеха: вижу краткий summary «что внутри + что пропустили + критичные допущения».

### 3.2 Аналитик (A-jobs)

**A-J1. Понять, откуда взялся вывод.**
> Когда я смотрю на конкретное требование/раздел в ТЗ и сомневаюсь,
> я хочу проследить — на основании чего система это написала: какая
> стадия методологии, какое правило сработало, какие входные данные.

Исход: открываю reasoning panel и provenance, вижу цепочку.

**A-J2. Поправить вопрос/ответ после факта.**
> Когда я понимаю, что я (или система) ответила не так — я хочу
> переоткрыть вопрос, перевыбрать вариант, дать новый ответ, чтобы
> система пересчитала.

Исход: нашёл вопрос в Inbox, сменил статус / ответ.
> ⚠ Сейчас **частично реализовано** — можно повторно открыть вопрос (`reopen`), но переснимка вниз по графу не делается. Это **известный пробел**, не в скоупе текущего редизайна (это backend-фича).

**A-J3. Ответить на вопросы среднего приоритета.**
> Когда я работаю в режиме `balanced`/`control`, я хочу пройтись по
> накопленным вопросам в Inbox в порядке приоритета и закрыть их пачкой.

Исход: открываю Inbox, фильтр open, иду сверху вниз.

### 3.3 Методолог (Me-jobs)

**Me-J1. Сменить методологию проекта.**
> Когда я понимаю, что текущая методология не подходит проекту, я хочу
> сменить её и убедиться, что новые задачи будут идти по новому
> процессу.

Исход: на вкладке методологии переключил pack, увидел уведомление.

**Me-J2. Проверить, что методология применяется правильно.**
> Когда я смотрю на задачу, я хочу видеть пройденные стадии методологии,
> сработавшие правила, и — если правило не сработало — почему.

Исход: открыл задачу, в reasoning panel вижу стадии; provenance показывает выполненные правила и не-выполненные с причиной.

### 3.4 Архитектор (Ar-jobs)

Через CLI. В UI — только смотрит провенанс при отладке нового pack.
**Не в скоупе редизайна.**

## 5A. JTBD v2 — после L1

> Заменяет §5 v1 (которая осталась как след). Каждый job: situation +
> motivation + outcome + emotional + negative. Критерий настоящего job:
> формулировка должна сохранять смысл, даже если PoV Generator завтра
> заменят на ручной труд — job описывает прогресс пользователя в жизни,
> не действие в системе.

### Главное изменение от v1

В v1 менеджер / аналитик / методолог / архитектор перечислены как 4
равноправные роли. По L1: **активный пользователь системы — только
менеджер**. Команда разработки — получатель артефакта, не co-worker.
«Аналитик» = тот же менеджер в режиме «копать». «Методолог» — admin,
работает с реестром методологий отдельно от проектного цикла.
«Архитектор» — через CLI.

Это **упрощает дизайн**: оптимизируем один основной сценарий, не четыре
параллельных.

### M-J1. Передать команде задачу так, чтобы она знала ЧТО строить

- **Situation:** прилетел бриф / письмо / описание системы / ответы
  заказчика — нужно превратить это в техническое задание, которое
  команда разработки заберёт в работу.
- **Motivation:** чтобы команда поняла «что строить», и не возвращалась
  с уточнениями через неделю.
- **Outcome:** через 3 дня обсуждение с командой даёт **конкретные**
  вопросы по реализации, не «это всё непонятно, переделывайте».
- **Emotional:** уверенность что не позорно отдал.
- **Social:** профессионально выгляжу перед командой.
- **Negative N1:** «через неделю команда возвращается с „это всё не
  то“ — потеряна неделя + репутация».

### M-J2. Доверять артефакту достаточно, чтобы отдать его дальше

- **Situation:** система автономно выдала артефакт; нужно решить —
  отдавать или ещё доработать.
- **Motivation:** убедиться, что нет очевидной ереси / галлюцинаций,
  при этом **не перечитывать всё построчно**.
- **Outcome:** знаю где сильное, где слабое; передаю осознанно
  (или возвращаю на доработку конкретных мест).
- **Emotional:** «я не отдал шлак».
- **Negative N2:** «отдал артефакт с глюком → команда поймала на
  стендапе → стыдно публично».

### M-J3. Снять блок, который держит проект

- **Situation:** система упёрлась в вопрос, без которого не может
  двинуться (выбор подхода, scope, ограничение).
- **Motivation:** разблокировать процесс **осознанно** — не наугад,
  но и не зависнуть на полчаса.
- **Outcome:** вопрос закрыт, проект двинулся, я понимаю что только что
  решил и как это повлияет.
- **Emotional:** «не я держу процесс».
- **Negative N3:** «срок поджимает, отвлёкся, не зашёл — проект стоял
  сутки из-за моего вопроса».

### M-J4. Распределить внимание между 3–5 параллельными проектами

- **Situation:** начало рабочего блока, в системе 3–5 живых проектов
  в разных стадиях.
- **Motivation:** понять «куда идти первым», не загружая в голову
  состояние каждого проекта.
- **Outcome:** правильная очередь действий: «этот ждёт меня, этот идёт
  сам, этот готов к передаче».
- **Emotional:** контроль ситуации, не «всё одинаково срочно».
- **Negative N4:** «всё кажется одинаково важным — парализован».

### M-J5. Поддерживать живой проект после передачи команде

- **Situation:** ТЗ ушло команде. Идёт реализация. Прилетают уточняющие
  вопросы, фидбек, иногда корректировки требований.
- **Motivation:** оставаться в курсе без перечитывания всего, и где
  нужно — обновлять артефакт / отвечать ссылкой «вот это решилось
  здесь».
- **Outcome:** на вопрос команды отвечаю за 5 минут, потому что система
  помнит «почему так решили».
- **Emotional:** «я в курсе своих проектов, даже которые ушли».
- **Negative N5:** «команда спросила → не помню → дёргаю систему →
  она тоже не помнит → выгляжу непрофессионально».

### M-J6. Защитить ход решений при оспаривании

- **Situation:** команда / руководство спрашивает «почему именно так?»,
  часто через дни/недели после прошедшего решения.
- **Motivation:** дать обоснованный ответ **без необходимости заново
  перечитывать весь проект**.
- **Outcome:** «вот это решилось здесь, вот данные, вот допущения, вот
  альтернативы что рассматривались».
- **Emotional:** компетентность.
- **Negative N6:** «не могу объяснить почему — выгляжу глупо».

### M-J7. Войти в контекст проекта быстро после паузы

- **Situation:** возвращаюсь к проекту через день / неделю / после
  выходных.
- **Motivation:** загрузить в голову «где он, что было сделано, что от
  меня ждут» — не за 10 минут чтения, а за 30 секунд сканирования.
- **Outcome:** через минуту работаю, не «снова всё разбираться».
- **Emotional:** эффективность, нет ощущения вязкости.
- **Negative N7:** «10 минут только на то, чтобы вспомнить где это».

### Сводка negative jobs (страхи)

| # | Страх | Закрывает job | Связь с challenge |

## 5B. Paradigm decisions (L4, ждут подтверждения)

> Решения, которые вытекают из L0 + L1 + L2. Каждое явное, с
> обоснованием. Подтвердить или возразить ДО перехода в L5 (IA):
> иначе IA построится на воздухе.

### P1. Sync default + async safety net (НЕ pure async)

- **Источник:** L1 C2 «обычно сидит и ждёт, иногда отвлекается».
- **Решение:** главный поток — синхронный. Запустил → смотришь как
  идёт → отвечаешь когда зовут. Async-нотификации (email / мессенджер /
  баннер при возвращении) — **safety net** на случай отвлёкся, **не**
  первичный канал.
- **Не выбираем:** pure-async «иди занимайся другим, мы пришлём push»
  — это для скептика и multi-project-агентов, не для «сидит и ждёт».

### P2. Multi-project home + single-project workspace

- **Источник:** L1 A1 «3–5 проектов», M-J4, M-J7.
- **Решение:** **корень навигации = home-дашборд «мои проекты сейчас»**
  с понятным статусом каждого. Клик в проект → глубокий workspace
  этого проекта.
- **Не выбираем:**
  - Один большой workspace на N проектов с переключателем.
  - Sidebar со списком проектов как корень (sidebar возможен внутри
    workspace, но не как главный экран).

### P3. Doc-centric: артефакт — главный объект экрана проекта

- **Источник:** L0 (категория = производит артефакт), L1 D3 «на
  крючке», M-J1 (передать), M-J5 (поддерживать).
- **Решение:** в экране проекта **главный объект = формирующийся /
  готовый артефакт**. Процесс (вопросы, граф задач, методология) —
  служебно, рядом или ниже, не центр.
- **Не выбираем:** dashboard с равноправными карточками (overview /
  вопросы / задачи / артефакты / методология). Это process-centric,
  который размазывает фокус.

### P4. Status-first навигация на home; object-first внутри проекта

- **Источник:** L1 A1+A2, M-J4.
- **Решение:** на home проекты сгруппированы **по статусу**:
  - 🔴 «Ждут меня» — блокирующие вопросы / приёмка
  - 🟢 «Идут сами» — running, не нужно сейчас
  - ✅ «Готовы к передаче» — артефакт готов, нужна моя приёмка
  - 📦 «На крючке» — переданы, ждут или ловят фидбек команды
  - 💤 «Завершённые» — свёрнутые архивные

  Внутри проекта — обычная структура (артефакт + вопросы + задачи),
  не по статусу.
- **Не выбираем:** chronological / alphabetical список без статусной
  группировки.

### P5. Failure surfacing > Trust display

- **Источник:** L1 E1 «доверие есть» + E2 «надо минимизировать риск»,
  L0 C4 vs C1.
- **Решение:** НЕ показывать общий «confidence score 0.82» рядом с
  артефактом. ВМЕСТО — **проактивная разметка подозрительных мест
  внутри артефакта**:
  - «этот раздел сгенерирован без подтверждения факта»
  - «здесь использовано допущение X»
  - «здесь методология не покрыла стадию»

  Менеджер сканирует артефакт глазами, видит выделения, точечно
  проверяет.
- **Не выбираем:**
  - Общий trust-score / зелёная иконка «всё отлично».
  - Полная разметка _каждого_ предложения (зашумит, потеряется важное).

### P6. Paste/upload first для входа в проект

- **Источник:** L1 F2 «обычно есть текст / бриф / описание».
- **Решение:** форма создания проекта = **большой textarea «вставь
  материал»** + опция загрузить файл. Можно вставить несколько кусков
  в один заход (бриф + ответы заказчика + описание системы). Система
  разбирает.
- **Не выбираем:** структурированная форма с 5+ полями
  (objective_ref, domain_pack_refs, methodology_pack, complexity)
  как первый экран. Эти параметры — в expert-режиме или определяются
  системой из материала.

### P7. История решений — first-class, не подвкладка timeline

- **Источник:** L1 D3 «на крючке», M-J5, M-J6, N5/N6.
- **Решение:** **«журнал решений проекта»** = отдельная навигационная
  сущность. Каждая запись: что решили, когда, на основании чего, какой
  альтернативный вариант рассматривали, чем повлияло на артефакт.
  Доступна через недели/месяцы после передачи.
- **Не выбираем:** растворить решения в общем timeline событий
  («событие 1: задача создана; событие 2: вопрос задан; событие 3:
  ответ выбран X») — там они теряются.

### P8. Версии артефакта — простые «снапшоты», не git-like

- **Источник:** L1 D3 «на крючке», M-J5 «обновлять по фидбеку».
- **Решение:** при существенных изменениях (после передачи, после
  ответа на новый вопрос) сохраняется **снапшот**: «v1 — отправлено
  команде 11.05», «v2 — после фидбека 14.05». Менеджер видит список
  версий, может сравнить diff важных полей.
- **Не выбираем:** полный git-like flow с ветвями / merge / rebase —
  overkill для one-user сценария.

### Открытые вопросы L4

- **P9?** Передача артефакта команде — отдельная кнопка «передать»
  (фиксирующая версию) или неформально (скопировал → отправил вне
  системы)? Зависит от того, важно ли системе знать про факт передачи.
- **P10?** Push-каналы — email / Slack / только баннер при
  возвращении? Зависит от того, что менеджер регулярно проверяет.

## 6. ⚠ HYPOTHESIS v1 — Ожидания пользователей

> **Заметка:** часть «ожиданий» ниже — это **преждевременные UX-решения**
> («одну главную вещь на экране», «hero + primary CTA», «карточка
> артефакта с preview»). Настоящие ожидания живут на уровне поведения
> и эмоций, не интерфейсных паттернов. Пересмотрим после уровней 1–4.

### 6.1 Менеджер ожидает

- **Простоту входа.** «Создать проект» = поле «опиши задачу» + кнопка. Без выбора `objective_ref`, `domain_pack_refs[]`, `methodology_pack_ref` руками.
- **Одну главную вещь на экране.** «Что мне делать прямо сейчас» — крупно и очевидно. Не 7 вкладок и таблиц.
- **Бизнес-язык.** «Вопрос», «допущение», «ТЗ», «согласовать с заказчиком». Не `clarification_candidate`, `default_assumption`, `quality_gate.human_approval`.
- **Прогресс понятен на глаз.** Не «3/12 листовых задач», а «3 из 5 шагов: сбор требований готов, открытые вопросы → черновик ТЗ → ревью → экспорт».
- **Уведомление о вмешательстве.** Если система ждёт меня — баннер. Не «зайди в Inbox раз в день».
- **Финальный результат как продукт.** ТЗ открывается «как документ», с человеческим форматированием. Не как `<pre>json</pre>`.

### 6.2 Аналитик ожидает

- **Drill-down на любую глубину.** Карточка → reasoning → правила → контекст. Без копания в json.
- **Контекст не теряется.** Когда открываю карточку задачи, я по-прежнему вижу, к какой цели она относится.
- **Подсветка «откуда».** Каждое поле артефакта связано с входным артефактом или правилом методологии (через `_source`).

### 6.3 Методолог ожидает

- **Технический язык OK.** Может видеть `stage_id`, `rule_id`, `fired/not_fired`.
- **Стадии = first-class.** Карта методологии с числами применений.
- **Сравнение прогонов.** ⚠ После MVP — не в скоупе.

### 6.4 Архитектор

Через CLI. UI ожидания минимальные: provenance работает, JSON копируется.

### Бизнес-вопрос 1: что менеджер ждёт после полного workflow?

### Бизнес-вопрос 2: engagement level per-project или per-user?

Это убирает «10 раз ставить autopilot», но сохраняет per-project управление для случаев «этот проект важный, поставлю control».

## 10. Anti-scope (валидно)

- **Не меняем backend контракты** ради UI (кроме мелких `view` добавок).
- **Не переделываем clarification reopen + retake** — это backend пробел (A-J2), отдельная задача.
- **Не делаем сравнение прогонов / diff методологий** — не в MVP.
- **Не подключаем CSS-фреймворк** — vanilla CSS + токены.
- **Не делаем свой компонент-кит** — конвенции поверх существующего.
- **Не убираем существующие URL** — `/state`, `/review`, `/debug` остаются, перенаправляются в новые табы Settings.

## 11. Уровень 1 — Открытые вопросы (нужны ответы заказчика)

Без ответов на эти вопросы все нижележащие уровни — гипотезы.
Группы вопросов и почему они важны:

### Группа A — Загрузка и параллельность

| # | Вопрос | Почему важно |
|---|---|---|
| A1 | Сколько проектов одновременно ведёт типичный менеджер? **1 фокусный / 2–3 / 5–10 / десятки** | 1 → workspace; 10+ → home-дашборд + поток нотификаций |
| A2 | Сколько проектов одновременно **активны** (требуют его внимания на этой неделе) | Где «middle of the pyramid» — главный экран должен показывать именно это |

### Группа B — Ритм работы

| # | Вопрос | Почему важно |
|---|---|---|
| B1 | Как часто менеджер заходит в систему? **Несколько раз в день / 1–2 раза в день / реже / только когда позвали** | Push vs pull paradigm полностью зависит от ответа |
| B2 | Сколько обычно проходит между сессиями работы по одному проекту? **Минуты / час / день / неделя** | Определяет нужен ли «возврат в контекст» (C3) и насколько подробный |
| B3 | Сколько времени менеджер тратит за одну сессию в системе? **5 мин / 15–30 / час+** | 5 мин → одна задача на экран; час+ → workspace-режим |

### Группа C — Среда и устройство

| # | Вопрос | Почему важно |
|---|---|---|
| C1 | Где менеджер работает? **Ноутбук в офисе / дома / в переговорке между встречами / с телефона** | Mobile-first или desktop-first; нужны ли уведомления вне системы |
| C2 | Когда система ждёт ответа — менеджер **сидит и ждёт / занят другим / не знает что его ждут**? | Push (email/мессенджер) обязателен, или достаточно бейджа в UI |

### Группа D — Социальный контекст

| # | Вопрос | Почему важно |
|---|---|---|
| D1 | Менеджер работает с проектом **один** или у команды тоже есть доступ? | Single-user workspace vs collaboration features |
| D2 | Кто получатель готового артефакта? **Команда разработки внутри / внешний заказчик / руководство для защиты / архив** | Формат экспорта, метафора «передачи», тип reader-режима |
| D3 | После передачи артефакта дальше — менеджер **продолжает быть на крючке** (отвечает на вопросы команды), или «отдал и забыл»? | Нужны ли follow-up функции, история выдач, версионирование |

### Группа E — Отношение к AI

| # | Вопрос | Почему важно |
|---|---|---|
| E1 | Какой уровень доверия к AI у менеджера **до** прихода в систему? **Скептик / нейтрально / любопытный / уже верит** | Скептику нужно постоянное show-your-work; верящему — наоборот, не мешать |
| E2 | Что произойдёт, если в финальном ТЗ окажется галлюцинация / ошибка? **Команда сразу поймает / встретят на встрече / попадёт в код / неприятно публично** | Где система должна страховать (C4 failure surfacing) и насколько настойчиво |

### Группа F — Запуск проекта

| # | Вопрос | Почему важно |
|---|---|---|
| F1 | Как менеджер обычно **приходит к новому проекту**? **Идея пришла → сам начал / задача спустилась сверху / встреча с заказчиком → закрепили** | Какие данные у менеджера на руках в момент создания, какая форма ему подходит |
| F2 | На момент создания проекта в системе — у менеджера **уже есть текст** (письмо, brief, протокол встречи), или он его пишет с нуля прямо здесь? | Paste-friendly textarea vs structured form vs upload файла |

## 11A. Зафиксированные ответы (L1, 2026-05-11)

| # | Ответ | Следствие для дизайна |
|---|---|---|
| **A1** | 3–5 проектов параллельно | Multi-project — главный экран показывает набор проектов, не один большой workspace |
| **A2** | Неизвестно — рабочая гипотеза: 2–3 из 5 активны на неделе | Главный экран ранжирует «требует внимания / идёт само / готово / спит» |
| **B1–B3** | Неизвестно. Рабочая гипотеза до наблюдения: несколько раз в день, сессии 15–30 мин, между сессиями час–день | Проверится через L8 (прототип + использование). Сейчас не критично |
| **C1** | Офис | Desktop-first. Mobile не критично |
| **C2** | Обычно сидит и ждёт, **иногда отвлекается** | **Sync default + async safety net** (P1): главный поток синхронный, async — на случай отвлёкся |
| **D1** | Один пользователь работает с проектом | Single-user workspace. Без collaboration features |
| **D2** | Внутренняя команда разработки | Экспорт: markdown / Confluence / Notion. PDF / презентация — не первичны |
| **D3** | **На крючке** после передачи: отвечает на вопросы команды | Артефакт **живёт после передачи**. Версии (P8) + журнал решений (P7) — first-class |
| **E1** | Доверие | Не нужен skeptic-mode с постоянным «show your work». Можно делегировать |
| **E2** | Команда сразу поймёт ошибку, но **надо минимизировать** | **Failure surfacing > Trust display** (P5): не общий score, а проактивная разметка подозрительных мест внутри артефакта |
| **F1** | По-разному (сам / задача / встреча) | Форма создания не должна форсировать «как пришёл» |
| **F2** | **Обычно есть текст / бриф / ответы / описание** на старте | **Paste/upload first** (P6): textarea принимает sloppy multi-input, не структурированная форма |

### Ключевые сигналы для нижних уровней

1. **Тип взаимодействия = sync с async safety net.** Pure-async paradigm отпадает.
2. **Multi-project, но не massive scale.** 3–5 → home-дашборд проектов как entity, не «inbox всех вопросов всех проектов».
3. **Артефакт — живой объект жизненного цикла**, не одноразовый deliverable. С учётом «на крючке» — нужен post-handoff режим (журнал, версии, lookup).
4. **C4 (failure surfacing) — главный challenge.** Не C1 (trust calibration). Доверие есть, но риск репутации → выделять подозрительные места, а не показывать общий score.
5. **Менеджер — единственный активный пользователь системы.** Аналитик / Методолог / Архитектор не работают параллельно с ним в одном проекте. **Упрощает дизайн**: один сценарий, не четыре.
6. **Вход = вставка материала**, не структурированная форма.
